## [Не выпущено]

### Ломающие изменения

- Коды возврата приведены к единому правилу: `0` — успех, `1` — команда сообщила об отказе, `2` — ошибка разбора аргументов, `128 + номер сигнала` — прерывание. Раньше кодом `0` завершались `account remove` с неизвестным именем, `auth check` с непригодным аккаунтом, `tg send` при недоставке, `tg download` для отсутствующего сообщения, `state reset` для чата без состояния, `tg info` с ошибками запроса, а также `run` с ошибками экспорта. Прерывание по Ctrl+C вне цикла экспорта теперь тоже даёт `130`, а не `0` или `1`. Таблица кодов добавлена в README.
- Неверная форма вызова завершается кодом `2` с блоком usage, а не кодом `1` без него: `run --require-takeout --no-takeout`, `tg send` без `--text` и `--file`, `state reset` без `chat_id` и без `--all`. Соседний случай в том же наборе -- `tg messages --truncate 5 --no-truncate` -- давал код `2` и подсказывал, как команду следовало вызвать, а эти три отказывали строкой без usage. Правило записано в CONTRIBUTING: форма вызова -- `click.UsageError`, состояние системы -- `_fail`.
- Экспорт аккаунта идёт в подкаталог с его alias: `output.path` -- базовый каталог, итоговый путь `{path}/{alias}/`, как и было описано в документации. Прежде alias в путь не добавлялся и попадал туда только потому, что шаблон, создаваемый `init`, зашивал его в само значение; конфиг, написанный руками по документации или оставленный со значением по умолчанию `./export_output`, давал двум аккаунтам один каталог, одну базу состояния и переиспользование чужих файлов при дедупликации. Уже сделанные выгрузки остаются на месте: alias не добавляется, если последний элемент пути совпадает с ним или если каталог уже содержит базу состояния. Опция `--output` по-прежнему задаёт каталог экспорта целиком.
- Каталог конфигурации подчиняется стандарту XDG Base Directory (`XDG_CONFIG_HOME`) и может быть задан напрямую переменной `TG_EXPORT_CONFIG_DIR`. Прежде путь `~/.config/tg-export` был зашит, и держать раздельные наборы аккаунтов, сессий и учётных данных было нечем: `--config` переопределяет только конфиг аккаунта.

### Добавлено

- `--json` появился у `tg messages`, `config` и `account default` -- флаг машиночитаемого вывода теперь есть у всех запросных команд. У `tg messages` это массив объектов с полями `id`, `date`, `sender`, `text`, `media`, `action`: прежде вывод разбирался регулярным выражением по строкам, и первое же многострочное сообщение построчный разбор ломало; обрезка текста в этом режиме по умолчанию не применяется, а тип медиа и вид системного сообщения стоят отдельными полями, а не приписываются к тексту. У `config` это сводка настроек и аккаунтов (с `-v` -- ещё и блок `settings` по каждому аккаунту), причём `api_hash` в неё не попадает: четыре его знака в терминале нужны лишь для того, чтобы отличить одни учётные данные от других.
- `auth check` и `takeout clear` принимают аккаунт и опцией `--account`, а не только позиционным `NAME`. Остальные девять команд знают только опцию, поэтому обёртка, подставляющая `--account "$ALIAS"` во все вызовы, на этих двух отказывала. Прежнее позиционное написание принимается; указание двух разных имён сразу отвергается кодом `2` с блоком usage.
- `SECURITY.md`: поддерживаемые версии, приватный канал сообщения об уязвимости (private vulnerability reporting на GitHub) и перечень того, что нельзя прикладывать к сообщению. Форма заведения issue предлагает этот канал ссылкой, а предупреждение в шаблоне отчёта об ошибке дополнено `api_id`, `api_hash` и файлом сессии. Прежде у нашедшего проблему оставался единственный маршрут -- публичный issue, то есть раскрытие до выпуска исправления.
- Опция `run --rerender`: HTML пересобирается по всем чатам, включая те, в которых ничего не изменилось. Рендер неизменившегося чата пропускается -- иначе каждый запуск перечитывал всю базу и собирал страницы заново, -- и следствием было то, что после обновления шаблонов такие чаты оставались собранными прежней версией, а способа заставить пересборку не было. README при этом обещает пересоздание HTML без обращения к Telegram API.
- Опция `run --no-takeout`: Takeout не запрашивается вовсе, экспорт сразу идёт через обычный API. Прежде единственным способом обойтись без Takeout было дождаться отказа и положиться на автоматический переход; запрос при этом стоит обращения, на которое Telegram отвечает кулдауном до суток. Вместе с `--require-takeout` флаг отвергается: они просят противоположного.
- В корне репозитория появился `config.example.yaml` — рабочий пример конфигурации со всеми разделами, который загружается как есть; прежде полные примеры жили только в `docs/configuration.md`. Шаблон, который печатает `tg-export init`, дополнен разделами `archived` и `import_existing`: они разбирались кодом и были описаны в документации, но в шаблоне — основном способе познакомиться с составом настроек — не упоминались. Полнота примера и шаблона закреплена тестами: раздел, который понимает загрузчик и не называет ни один из них, роняет проверки.
- `-h` работает как синоним `--help` во всех командах и группах: прежде он завершался кодом 2 с сообщением «No such option: -h».
- У `state reset --all` появилось подтверждение и флаг `--yes`. Перед сбросом печатается число затрагиваемых строк по таблицам базы состояния; с `--delete-messages` команда выполняла `DELETE FROM messages` и `DELETE FROM files` по всей базе без показа объёма и без вопроса, а опечатка в команде обходилась повторной выгрузкой всего аккаунта. Сводка печатается как существенная и не подавляется `--quiet`, иначе вопрос задавался бы без единой строки контекста.
- Команда `list` принимает `--json` -- краткая форма `--format json`, одинаковая с `account list`, `auth check`, `state show` и `tg info`.
- Инструкция по установке в README приведена в рабочее состояние. Примеры быстрого старта записаны без префикса `uv run`: пакету, установленному из PyPI, каталог проекта недоступен, и первая же команда завершалась ошибкой `Failed to spawn: tg-export`; для работы из исходников префикс объявлен отдельной оговоркой. Установка из исходников описана как `git clone` + `uv sync` -- прежде предлагалась `uv pip install -e .`, которая на свежем клоне падает с `No virtual environment found`, поскольку окружения не создаёт. Установка дополнения для прокси показана в кавычках: в zsh квадратные скобки без них трактуются как шаблон имени файла.
- Скрипт `scripts/check.sh` прогоняет весь набор проверок CI одной командой: `uv lock --check`, `ruff check`, `ruff format --check`, `pyright`, тесты с покрытием и границы покрытия по модулям; `scripts/check.sh --fix` предварительно исправляет исправимое (`ruff check --fix`, `ruff format`). Прежде проверки набирались вручную по трём командам, команда исправления формата нигде не называлась, и шаг `Format check` ломался коммитом, а выяснялось это только на CI. Расхождение скрипта с workflow ловится тестом: шаг, добавленный в CI и не добавленный в скрипт, роняет проверки.
- Релиз проверяется до необратимой публикации. Перед сборкой `publish.yml` прогоняет тот же набор проверок, что и CI на master (`scripts/check.sh`: синхронизация `uv.lock`, линтер, формат, типы, тесты, границы покрытия) -- прежде на релизном пути был только `pytest`, а `ci.yml` на push тега не срабатывает, поэтому тег на коммите с рассинхронизированным `uv.lock` или с ошибками типов публиковался беспрепятственно. Скрипт `scripts/release_notes.py` сверяет имя тега с версией в `pyproject.toml` и наличие непустого раздела в `CHANGELOG.md`, после чего готовит release notes; сверка идёт до загрузки на PyPI, тогда как прежняя проверка `test -s release_notes.md` стояла ниже неё -- отсутствующий раздел давал опубликованную версию, отсутствующий GitHub Release и красный workflow, а отката у PyPI нет.
- Команда `tg info` принимает `--json`: результат по всем чатам выводится в stdout одним документом, как у `account list`, `auth check` и `state show`. Прежде машиночитаемый результат можно было получить только записью в файл (`--output`), в конвейер он не отдавался. Счётчик обработанных чатов переведён в stderr -- `tg info ... | grep` получал вперемешку данные и служебные строки.
- Справочник команд `docs/cli.md`: назначение, опции, поведение и коды возврата всех девятнадцати команд. Прежде документация проводила пользователя только по девяти из них, а `config`, `verify`, `takeout clear`, `tg send`, `tg download`, `state show`, `state reset`, `account list`, `account remove` и `auth check` не были описаны нигде, кроме `--help`. Полнота справочника закреплена тестом: команда, добавленная в код и не описанная в справочнике, роняет проверки.
- Опция `run --require-takeout`: отказ Takeout завершает команду ошибкой вместо перехода на обычный API. Без флага поведение прежнее -- переход выполняется, но теперь он объявляется как существенное сообщение (видно и под `--quiet`), а использованный режим печатается в итоговой сводке строкой `API:`.
- Команда `tg send` принимает `--as-document`: файл отправляется без сжатия, как документ.
- Прогресс отправки файлов в `tg send`.

### Изменено

- `config` показывает прокси так, как его читает экспорт, а не как записано в файле: опечатка в имени ключа давала порт `None` в выводе команды и подстановку умолчания при выгрузке, а прокси, записанный одной строкой вместо секции, завершал команду трассировкой `AttributeError`. Негодная запись показывается как `invalid: <причина>` — так же, как это уже сделано для `min_free_space`. Блок `settings` у `config -v --json` содержит те же разделы, что и текстовый вывод (правила, папки, чаты, флаги общих данных, `unmatched`, `left_channels`, `archived`, `import_existing`), причём правила отдаются структурами, а не подписями: раздела, которого в выводе нет, для читающей программы не существует.
- `purge` отчитывается об удалённом в той же форме, в какой предупреждал: `Deleted from DB: messages=7, files=3, ...` вместо представления словаря Python со скобками и кавычками — пользователь сравнивает «сколько собирались удалить» и «сколько удалили» без пересчёта. Размер каталога перед вопросом считается тем же способом, что и в сводке экспорта (`du`), а не обходом с обращением к каждому файлу: у чата с десятками тысяч файлов это была пауза перед самим вопросом, причём переиспользованные по жёсткой ссылке файлы завышали обещанное освобождение места. Когда `du` недоступен, строка размера опускается.
- `account default` печатает в stdout только само имя аккаунта, пояснение уходит в stderr. Прежде туда шла строка `Default account: <alias>`, а при незаданном аккаунте -- `No default account set.`, поэтому `NAME=$(tg-export account default)` получал пояснение как значение. Когда аккаунт по умолчанию не задан, stdout пуст, а код возврата остаётся `0` -- как у `account list` без аккаунтов.
- Гейт релиза сверяет дату раздела `CHANGELOG.md` с датой коммита, на который указывает тег (допуск -- сутки на часовые пояса и на разрыв между подготовкой и пушем). Прежде проверялась только форма даты, поэтому дата, скопированная из предыдущего раздела при переименовании «Не выпущено», проходила и становилась заголовком release notes на GitHub; отличить это от двух релизов за один день по файлу нельзя.
- Скрипт гейта без `--output` печатает release notes в stdout и файла не создаёт. Прежде умолчанием был `release_notes.md` в текущем каталоге, а `.gitignore` его не знал: локальная проверка гейта без флага оставляла файл в корне рабочего дерева, откуда его забирал `git add -A` релизного коммита. Имя добавлено в `.gitignore` -- в конвейере публикации файл пишется в рабочее дерево явным флагом.
- Публикация на PyPI выполняется из окружения `pypi`. Без окружения удостоверение OIDC выпускается любому прогону workflow; имя окружения указывается у доверенного издателя на стороне PyPI и сужает доверие до прогонов в нём, а также даёт место для ручного подтверждения перед необратимым шагом. Порядок шагов не изменился.
- Верхняя граница `python-socks<3` объяснена проверяемым фактом вместо «сочетание не испытывали»: в 3.0.0 у `AsyncioProxy` удалены публичные свойства `proxy_host` и `proxy_port`, к которым обращается Telethon 1.44 в `network/connection/connection.py`. Проект в эту ветку Telethon не попадает (она требует `local_addr`), поэтому в комментарии названо и это -- граница держится до того, как Telethon объявит поддержку 3.x.
- Документация настройки `media.concurrent_downloads` объясняет, откуда взят потолок в пять загрузок: это осторожность, а не ограничение Telegram -- выше пяти экспорт не проверялся, загрузки делят одно соединение и каждая держит свой буфер. Прежде и таблица настроек, и комментарий у констант называли только сам диапазон, поэтому поднять границу можно было правкой константы без понимания, чем это ограничено.
- Опция `init --output` переименована в `--output-file`, прежнее написание принимается. Во всех остальных командах `--output` означает каталог, поэтому `tg-export init --output ~/configs` создавал файл с именем `configs` вместо файла внутри каталога. Описание каталога экспорта сведено к одной формулировке: у `run` оно отличалось от четырёх соседних команд.
- Подсказку «как создать конфигурацию» печатает каждая команда, которой конфигурация нужна. `verify`, `state show`, `state reset` и `purge` отказывали голым «Config not found», а строку `Create it with: tg-export init --account <alias>` знала одна `run`; теперь она объявлена рядом с самой проверкой и приходит от всех пяти.
- `state reset <chat_id> --delete-messages` печатает объём удаляемого и спрашивает подтверждение, как `purge` и `state reset --all`. Сообщения и записи о файлах чата удалялись молча, а `--yes`, объявленный в справке безусловным пропуском подтверждения, для одного чата пропускать было нечего. Сброс без `--delete-messages` обратим и вопросов не задаёт, текст справки `--yes` уточнён до «Skip confirmation for destructive resets».
- Релизный конвейер переживает отказ после публикации. Тег сверяется с историей `master` до сборки: workflow срабатывает на любой тег `v*`, а проверки о ветках ничего не знают, поэтому тег на рабочей ветке опубликовал бы версию, содержимого которой в `master` нет. Загрузка на PyPI объявлена `skip-existing`, создание GitHub Release идемпотентно -- повторный запуск после сбоя на последнем шаге теперь дорабатывает релиз, а не упирается в «файл уже существует». Бюджет времени сборочного задания поднят до двадцати минут: у него больше работы, чем у одного элемента матрицы CI, а таймаут между загрузкой и созданием release -- та же необратимая точка. В `RELEASING.md` добавлен раздел «Восстановление после отказа», в шаге 3 названо обновление оглавления CHANGELOG, и соответствие оглавления разделам закреплено тестом.
- Границы покрытия по модулям подтянуты к фактическим значениям с единым отступом в пять пунктов и правилом пересмотра в комментарии: у крупнейших модулей запас доходил до сорока пунктов, то есть по своему назначению -- ловить регрессию -- таблица для них не работала (снятый файл тестов ронял покрытие `cli/export.py` с 70,7 % до 52,6 % и проходил прежнюю границу 45 %). Нижняя граница Telethon поднята до 1.43: схема сессии v8, которую обходит `FixedSQLiteSession`, и проверка python-socks, на которой стоит дополнение `proxy`, появились только там, а на 1.36--1.42 собственный тест схемы сессии красный. Убрана строка-комментарий о версии codecov-action, противоречившая пину двумя строками ниже.
- Конвенции проекта названы в CONTRIBUTING таблицей «Конвенции, которые удерживают тесты»: правило, что оно запрещает и какой тест его держит. Прежде о пределе длины функции или о запрете своего SQL в командах человек узнавал по красной проверке -- уже после того, как код написан; полнота таблицы закреплена тестом. Стартовый конфиг перестал повторять умолчания: шаблон `tg-export init` собирается из значений загрузчика, а совпадение шаблона и `config.example.yaml` с этими значениями проверяется -- смена умолчания в коде больше не оставляет артефакты, утверждающие прежнее. Роли шаблона и примера разведены в docstring: пример -- статичная отправная точка, шаблон -- под список чатов конкретного аккаунта.
- Записано то, что раньше знал только автор кода. Формат JSON-колонок таблицы `messages` описан в `models.py` и в разделе CONTRIBUTING о схеме базы: имена dataclass и их полей входят в формат хранения, поэтому переименование требует того же внимания, что и правка DDL. У `Exporter` и `ExportState` появились описания класса -- порядок фаз и группы методов; ветка чтения записи без маркера класса объявлена страховкой и закреплена тестом. Окно принудительного завершения получило имя (`FORCE_SHUTDOWN_WINDOW_SECONDS`), а README и справочник команд приведены к фактическому поведению: немедленно прерывает второй Ctrl+C в течение трёх секунд, позже -- это новая просьба остановиться мягко.
- Словарь статусов файла записан один раз. Значения колонки `files.status` объявлены перечислением `FileStatus` в `models.py` рядом с остальными: прежде `done` жило литералом в четырёх местах, а список значений колонки был выписан ещё раз строками -- при том, что два из них дублировали члены `DownloadStatus`. Проверки не дают вернуть литерал и следят, что два словаря совпадают там, где пересекаются. Заодно константы, которые читались выше своего объявления (`_ALL_SUFFIX` в разборе `--log-level DEBUG:all`, списки известных ключей секций конфигурации), подняты над читающими их функциями, а проверка чтения файлов в UTF-8 распространена на каталог `scripts/`, где нашлось одно чтение в кодировке локали.
- Убраны три слоя без собственного поведения: проверка имени аккаунта на `.` и `..`, недостижимая после проверки по шаблону (первый символ обязан быть буквой или цифрой), и две приватные обёртки, переадресовывавшие вызов одной строкой. Обработчик `SystemExit` в `scripts/release_notes.py` повторял поведение интерпретатора и при этом переписывал код возврата: запуск с неверными аргументами давал `Error: 2` и код 1 вместо кода 2 и строки usage от argparse.
- Комментарии и docstrings приведены к одному стилю: остаётся причина и ограничение, а не пересказ следующей строки и не рассказ о прежних версиях. Убраны двадцать шесть подписей вида `# Setup renderer` перед `renderer = HtmlRenderer(...)`, три баннера-разделителя (один описывал команды, переехавшие в другой модуль при разбиении `cli.py` на пакет) и количественные подробности прошлых правок из пяти docstrings. Пять помощников команд начинались пустой строкой вместо docstring -- теперь у каждого есть описание. Оба расхождения закреплены проверками: файл не заканчивается комментарием, тело функции не начинается пустой строкой.
- Документация приведена в соответствие с интерфейсом, и каждое соответствие закреплено тестом. Раздел «Полный конфиг» в `docs/configuration.md` -- это дословно `config.example.yaml`: прежде он объявлялся тем же примером, а тексты разошлись по правилам типов, составу папок и чатов и по `import_existing`, причём загружается и проверяется только файл. Примеры связки «выгрузить каталог -- построить конфиг» записаны каноническими именами опций (`--output-file`, `--from-catalog`) вместо написаний, оставленных для совместимости; их же называет сводная таблица `docs/cli.md`. Перечень команд с `--json` в README дополнен командой `list`. Конвенции ADR называют статус одним словарём (`принято` / `заменено ADR-NNNN` / `устарело`), и значение статуса теперь сверяется с ним. Строки документации в коде называли несуществующие команды `tg chats` и `tg takeout clear` -- вместо `list` и `takeout clear`; проверка ловит такое упоминание в любом файле пакета.
- `tg-export config -v` показывает конфигурацию целиком и читает её тем же кодом, что и экспорт. Добавлены строки `archived`, `import_existing`, семь флагов глобальных данных, `defaults.media.concurrent_downloads` и `defaults.export_service_messages`: раздела, которого нет в выводе, для пользователя не существует, а проверить действующее значение `archived.action` -- попадут ли в выгрузку архивные чаты -- было нечем. Лимит размера печатается человекочитаемой величиной: `500KB` показывался как `0MB`. Свободное место сообщается для каталога выгрузки -- путь брался разбором YAML напрямую, без раскрытия `~` и без alias аккаунта, поэтому строка относилась к текущему рабочему каталогу, а не к разделу, куда пишется экспорт. `min_free_space` печатается разобранным значением, а запись, которую отвергает `parse_size`, называется неверной: прежде она показывалась как действующая настройка, тогда как `run` на ней отказывал.
- Документация разработчика приведена в соответствие с фактическим поведением: CONTRIBUTING описывает, что линтер, проверка типов и границы покрытия считаются на каждой версии матрицы CI (а не только на 3.12), и называет способ частичного прогона тестов -- `--no-cov`, без которого запуск одного файла завершается кодом 1 при всех зелёных тестах. Шаблон отчёта об ошибке показывает готовую форму `tg-export --debug <команда>`: флаг объявлен у корневой группы, и дописанный к подкоманде он давал «No such option '--debug'». Все три утверждения закреплены тестами.
- Проверка целостности (`verify` и `run --verify`) забирает сообщения битых файлов пачками по чатам и перекачивает их с той же ограниченной параллельностью, что и экспорт (`concurrent_downloads`). Прежде каждому файлу доставался отдельный круг «запрос -- ответ», а скачивание шло строго по одному: настройка параллельности к пути проверки не применялась вовсе. Оба пути проверки теперь пользуются одной реализацией и в этом.
- `tg info` разрешает идентификаторы чатов одним запросом и опрашивает истории с ограниченной параллельностью. Режим `--from-catalog --type` заведён ради пакетного опроса, но исполнялся поштучно: идентификатор, которого нет в кэше сессии, стоит `get_entity` отдельного запроса, и на каталоге в сотни чатов набегало столько же последовательных круговых задержек. Порядок вывода прежний -- тот, в котором чаты перечислены. Если пакетное разрешение отказало (оно падает целиком при одном непригодном идентификаторе), остаётся поштучный проход, который называет отказавший чат и сохраняет остальные.
- Месяц чата читается в порядке, согласованном с индексом по дате: `ORDER BY date, msg_id` вместо `ORDER BY msg_id`. Прежний порядок заставлял SQLite сортировать месяц целиком через временное B-дерево, складывая туда полные строки с шестью JSON-колонками, то есть при `temp_store = MEMORY` удваивал пик памяти на месяц -- ровно то, что потоковый рендер обещает держать пропорционально одному месяцу. Порядок показа при этом стал хронологическим и в чатах, где идентификаторы разошлись с датами после миграции группы в супергруппу.
- Соседние базы состояния, из которых берутся уже скачанные файлы, открываются один раз на весь экспорт, а не на каждый файл и каждую базу. Открытие стоит обращения к файлу, чтения схемы и холодного кэша страниц -- тот же довод, по которому рендер держит одно соединение на чат. Соединения получают общие прагмы чтения и закрываются вместе с остальными ресурсами прогона.
- Перевод фрагментов текста, реакций, сведений о пересылке и кнопок в JSON идёт без `dataclasses.asdict`. Эти типы плоские, и `asdict` покупал в них только рекурсивное копирование, которого `json.dumps` не требуется: 2,35 мкс против 0,08 мкс на объект по замеру, то есть единицы секунд процессорного времени на чате в полмиллиона сообщений -- в потоке цикла событий, где в это время не обслуживаются загрузки. Формат хранения не изменился и закреплён тестом.
- Версия `uv` в релизном workflow закреплена (`0.12.5`) и повышается сознательно: SHA-пин закрепляет загрузчик, но не сам инструмент, а в задании публикации `uv` собирает пакет рядом с правом выпуска в PyPI. В CI версия по-прежнему плавающая -- это решение записано комментарием: несовместимость с новым `uv` должна обнаруживаться на прогоне, а не при выпуске.
- Язык артефактов выбран по читателю и записан в CONTRIBUTING таблицей. Код пакета, манифест, сборочные сценарии и workflow -- английский (их читает всякий, кто берёт пакет с PyPI); тесты, документация, шаблоны issue и сообщения коммитов -- русский. Прежде `pyproject.toml` и `scripts/` смешивали оба языка внутри одного файла, а конвенция не была записана нигде. Граница закреплена тестом: кириллица в коде пакета, манифесте, скриптах или workflow роняет проверки.
- Ещё четыре места приведены к конвенциям модулей. Обрезка имени файла под колонку прогресса задавалась двумя несвязанными числами (40 и 37) -- теперь ширина одна, а срез вычисляется из неё. Умолчания прокси (`socks5`, `127.0.0.1`, `1080`) вынесены в именованные константы рядом с остальными в `auth.py`. Обновление строки каталога чатов идёт через `excluded`: одиннадцать колонок перечислялись в запросе четырежды, а значения передавались двумя одинаковыми наборами, и добавление колонки требовало четырёх согласованных правок. Подпись правила в `tg-export config -v` собирает один помощник -- прежде блок был скопирован для правил типов и правил чатов, и копии разошлись оформлением диапазона дат.
- Устранены четыре копипаста в путях вывода. Ветка `custom_emoji` в рендере текста дословно повторяла финальный `else` (ruff такое не ловит: `SIM114` сравнивает только соседние `elif`). Ключ-заглушка месяца для сообщений без даты выписывался литералом `"0000-00"` в шести местах двух модулей -- теперь это `UNKNOWN_MONTH_KEY` в `state.py`, который владеет форматом ключа, и смена значения не может оставить подпись «Unknown date» позади. Формат времени `%Y-%m-%d %H:%M` и разбор поля, приходящего то `datetime`, то unix-меткой, собраны в `format_moment` (`tg_export/format.py`) -- прежде блок разбора был скопирован для сессий приложений и веб-сессий целиком. Сборка пары «отправитель, текст» для списка сообщений вынесена в один помощник: `tg info` резал текст литералом 200, тогда как `tg messages` -- настройкой `DEFAULT_MESSAGE_TEXT_LENGTH`; заодно `tg info` показывает служебные сообщения действием, а не пустым текстом.

Выгрузка контактов и сессий собирает для тех же данных обычные словари, а типы остались от прежней схемы и читались как описание формата выгрузки; ruff такие остатки не ловит.

Шестнадцать действий собирались как `ActionChatCreate(type="ActionChatCreate", ...)`, и переименование класса оставило бы литерал прежним молча -- значение уходит в базу состояния и в шаблоны, где сверяется по строке. Цепочка из шестнадцати `if` заменена таблицей фабрик по образцу соседней таблицы простых действий. Соответствие имён закреплено двумя тестами: `type=` строкой в `converter.py` и расхождение имени модели с именем действия Telegram роняют проверки.
- Номер версии сверяется с содержимым раздела CHANGELOG. Гейт проверял тег, версию манифеста и наличие непустого раздела, но не то, соответствует ли выбранный номер накопленному: смена кодов возврата, каталога выгрузки и каталога конфигурации могла выйти под patch-номером, а отката у PyPI нет. В CHANGELOG заведена категория «Ломающие изменения», три такие записи вынесены в неё, и `scripts/release_notes.py` отказывает до публикации, когда раздел с этой категорией выпускают без бампа major, а раздел с «Добавлено» -- под patch-номером.
- Релизный конвейер разложен на три job'а, права выданы по задачам. GitHub кладёт переменные запроса OIDC-токена в окружение каждого шага job'а с `id-token: write`, поэтому в едином job'е обменять их на upload-token PyPI мог любой шаг -- включая `uv sync`, исполняющий build-backend'ы зависимостей, и прогон тестов; компрометация зависимости из `uv.lock` давала не сломанный релиз, а выпуск произвольного пакета от имени проекта. Сборка и проверки идут с `contents: read` и отдают результат артефактами, публикация -- отдельный job без кода проекта, GitHub Release -- третий job с `contents: write`. Решение записано в [ADR 0007](docs/adr/0007-split-publishing-permissions.md).
- Имена флагов приведены к единому соглашению. `--output` везде означает каталог, а файл результата задаётся `--output-file` (`list`, `tg info`); файл каталога чатов во всех командах называется `--from-catalog` (прежде `init --from`); число показываемых сообщений -- `--limit`/`-n` (прежде `tg info --last`). Прежние написания принимаются как синонимы и перечислены в справке, поэтому существующие сценарии не ломаются.

Опции путей объявлены как `click.Path(path_type=Path)` -- параметр приходит в команду уже объектом `Path`, и семнадцать ручных преобразований `Path(...)` после разбора аргументов убраны. Флаги `--quiet`/`--debug` хранятся в одном месте: прежде `main()` писал их и в модульные переменные, и в `ctx.obj`, читались оба хранилища, а `ctx.obj["debug"]` не читался нигде. Стандартная библиотека (`json`, `os`, `shutil`, `subprocess`, `tempfile`, `hashlib`, `unicodedata`, `collections`) импортируется в шапке модуля, а не внутри функций: она уже загружена интерпретатором, а локальный `import logging` вдобавок перекрывал модульный `logger`; отложенными остались только тяжёлые зависимости, и граница закреплена тестом. Цикл событий берётся через `asyncio.get_running_loop()`.

- Счётчики по текущему чату собраны в отдельный тип `ChatCounters`. Прежде имена девяти счётчиков были записаны трижды -- как поля, как строковые ключи словаря-снимка и как имена девяти почти одинаковых свойств, -- причём чтение снимка через `.get(..., 0)` превращало опечатку в ключе в молчаливый ноль. Снимок строится по описанию полей, а тест сверяет, что каждому полю `ChatCounters` соответствует счётчик прогона.

Проверки `isinstance(d, dict)` в начале разбора правил заменены на явную ошибку конфигурации с указанием раздела: `type_rules: {personal: true}` теперь сообщает, что раздел должен быть отображением, а не падает трассировкой `TypeError`. Оба каталога в `ensure_dirs` обрабатываются одинаково -- прежде отказ `chmod` для каталога сессий не перехватывался.

Полный вывод библиотек включается суффиксом `:all` -- `--log-level DEBUG:all` или `LOG_LEVEL=DEBUG:all`.

- Ошибки команды `tg info` печатаются в stderr, а не в stdout: машиночитаемый вывод остаётся пригодным для конвейера.
- Takeout-сессия переиспользуется между запусками, а не создаётся заново каждый раз. Раньше экспорт завершал сессию в `finally` (`stop_takeout(success=True)`), а следующий запуск начинал новую, и Telegram отвечал на неё кулдауном `TAKEOUT_INIT_DELAY` до 24 часов -- то есть Takeout по построению работал не чаще раза в сутки. Теперь сессия открывается с `finalize=False` и по окончании экспорта только отпускается; сохранённый `takeout_id` на следующем запуске проверяется пробным запросом и, если сервер его ещё помнит, используется повторно без нового `InitTakeoutSessionRequest`. Непригодный `takeout_id` завершается и заменяется новой сессией, как прежде. Явное завершение сессии осталось за командой `tg takeout clear`, которая теперь закрывает её и на сервере, а не только стирает локальный идентификатор.
- Убран код, который никем не вызывался: двенадцать функций (`save_takeout`, `get_takeout`, `cache_user`, `get_user`, `get_catalog`, `set_meta`, `get_meta`, `load_messages_for_month` в модуле состояния; `iter_topic_messages`, `get_forum_topics` в обёртке API; `get_chat_names`, `find_files` в импортёре), а также вторая сериализация сообщения `Message.to_json` / `Message.from_json` -- состояние давно хранит поля в отдельных колонках, и обе реализации успели разойтись по составу полей. Из схемы state-БД удалены неиспользуемые таблицы `takeout`, `users_cache`, `meta` и индексы `idx_messages_grouped`, `idx_files_local_path`; у баз, созданных прежними версиями, они убираются при открытии. Форматирование скорости перенесено в `format.format_speed`, чтобы лестница единиц измерения задавалась в одном месте, а девять одинаковых ветвей разметки текста в HTML-рендере свёрнуты в таблицу классов.
- Соединение с Telegram и база состояния открываются через `async with`, а не ручной парой `connect()` / `finally: disconnect()`. Прежде этот блок был повторён в командах десять раз, и в `tg info` и `list` исключение, возникшее между подключением и входом в `try`, оставляло соединение открытым до конца процесса. `TgApi` и `ExportState` стали асинхронными контекстменеджерами; помощник `_connect_tg`, отдававший подключённый объект с оговоркой «вызывающий обязан закрыть», заменён на `_connected_api`, а `_open_state` -- на `_opened_state`. Общий пролог команд (разрешение аккаунта, чтение конфига, вычисление каталога вывода) вынесен в `_resolve_output`: сообщение о ненайденном конфиге больше не живёт в четырёх копиях, расходящихся при правках.
- Разобраны восемь функций длиннее ста строк; самые крупные из них складывались в один сценарий «запустить экспорт»: `Exporter.run` (259 строк), `Exporter.export_chat` (214) и `_run_export` (181). Из `run` выделены установка обработчиков сигналов, отбор чатов, шапка запуска, сборка виджетов прогресса и экспорт одного чата, а три замыкания форматирования статуса стали классом `StatusView`; `export_chat` разделён по границам фаз на `_fetch_new_messages` и `_fetch_old_messages` с отдельным рендером страниц; из `_run_export` вынесены сборка загрузчика и печать итогов. Ни одна функция пакета больше не превышает ста строк, и это закреплено тестом.
- CLI больше не выполняет SQL мимо слоя состояния: сводка по чатам и предпросмотр удаления перед `purge` читаются методами `ExportState.list_chat_states` и `count_chat_rows`. Список таблиц, привязанных к чату, объявлен один раз константой `CHAT_TABLES` -- прежде он был записан дважды, и правка схемы в одном месте давала purge, удаляющий не то, о чём он предупредил.
- Появилась карта пакета для тех, кто меняет код: раздел «Устройство пакета» в `CONTRIBUTING.md` с таблицей из семнадцати модулей, схемой потока экспорта и границами слоёв. У `cli.py` появился модульный docstring с перечнем групп команд и объяснением, зачем импорты сделаны внутри тел функций. Форматирование размеров CLI берёт из `tg_export.format`, а не через приватный псевдоним в `tg_export.exporter`.
- Зафиксированы пять архитектурных решений, принятых с момента появления практики ADR: переиспользование Takeout-сессии между запусками (0002), сверка схемы базы состояния с DDL вместо механизма миграций (0003), порядок проверок до необратимой публикации (0004), каталог выгрузки на аккаунт (0005), снимок начала чата вместо блокировки при чтении счётчиков потоком отрисовки (0006). Прежде в каталоге была единственная запись — о самой практике. Конвенции дополнены правилом «тело неизменяемо, статус обновляется» и признаком того, что заслуживает записи; полнота оглавления и состав разделов закреплены тестами.
- Заведены шаблоны обращений и правила общения. Шаблоны issue (отчёт об ошибке, предложение) и pull request предупреждают о том, что вставлять реальные данные Telegram — имена и идентификаторы чатов, номера телефонов, содержимое сообщений — в публичное обсуждение нельзя; прежде это требование стояло только в `CONTRIBUTING.md` и встречало автора уже после отправки. Ссылки внутри документации проверяются тестом: файл или заголовок, на который никто не ведёт, находится на прогоне, а не читателем. В `RELEASING.md` и `CONTRIBUTING.md` описана уборка артефактов сборки: каталог `build/` — копия пакета на момент сборки, из-за которой поиск по репозиторию находит каждое имя дважды, и второе совпадение устаревшее.
- Инструменты разработки приведены к тому, на чём проект действительно проверяется. Нижние границы dev-зависимостей отставали на мажор и более (`pytest>=8.0` при 9.x, `pytest-asyncio>=0.23` при 1.x, `pytest-cov>=5.0` при 7.x, `ruff>=0.7` при 0.16), из-за чего окружение, поднятое без lock-файла, получало другие инструменты. Обновлён `uv.lock`: telethon 1.44.0, click 8.4.2, ruff 0.16.4, pytest 9.1.1, pyright 1.1.411; верхние границы рантайм-зависимостей остаются верны, обход дефекта порядка колонок в файле сессии по-прежнему нужен — в telethon 1.44.0 запись остаётся позиционной. Пины GitHub Actions подняты до актуальных версий (checkout v7.0.1, setup-uv v10.0.1, pypi-publish v1.14.2, codecov-action v7.0.0).
- Публикация выполняется с аттестациями PEP 740: параметр задан в `publish.yml` явно, а не оставлен на умолчание действия — умолчание может измениться, а публикация необратима. В `RELEASING.md` описана подпись тега ключом GPG или SSH и разница между подписью тега и аттестацией артефакта.
- Объявлены границы платформы и рантайма. В метаданных пакета появились классификаторы: поддерживаемые версии Python (3.11-3.14) и операционные системы (Linux, macOS); прежде `requires-python = ">=3.11"` без верхней границы обещал и версии, на которых проект не проверялся. Матрица CI дополнена Python 3.14, а совпадение классификаторов с матрицей закреплено тестом. В README указано требование Python 3.11 или новее и сказано, что на Windows проект не проверяется: там нет `fcntl`, и блокировка файла сессии вырождается в отсутствующую. В `CONTRIBUTING.md` перечислены проверяемые версии и платформа.
- Статические проверки стиля переведены с регулярных выражений на разбор синтаксического дерева. Проверка `_log` искала тело функции регулярным выражением и проверяла его только при совпадении: переименование, декоратор или иное форматирование — и она молча переставала что-либо проверять. Каждая переведённая проверка испытана на заведомо нарушающем коде, отсутствие искомой функции теперь само по себе отказ. Прогресс отправки не рисуется поверх уже запущенного живого виджета: rich отображает только верхний, и вложенный бар стоил бы обновлений, ничего не показывая.
- Исходы загрузки медиафайла объявлены перечислением `DownloadStatus` и разбираются таблицей счётчиков: прежде это была цепочка `elif` без завершающей ветки, и новый исход прошёл бы мимо статистики — сводка молча разошлась бы с тем, что лежит на диске. Неизвестный исход теперь попадает в журнал предупреждением, а полнота таблицы закреплена тестом. Значения статусов не изменились.
- Записаны мотивы решений, которые при следующем чтении восстанавливались бы заново: почему размер выгрузки считает `du`, а не обход дерева в Python (сотни тысяч файлов и учёт жёстких ссылок), и почему выгрузка Telegram Desktop разбирается регулярными выражениями, а не `html.parser` (из страницы нужны два атрибута, разбор идёт построчно без удержания документа в памяти). Недостижимый `return None` после цикла повторов заменён явным отказом. Убрана регистрация конвертера sqlite3 для `TIMESTAMP`: конвертер работает только при `detect_types=PARSE_DECLTYPES`, которого ни одно соединение проекта не открывает, — регистрация обещала разбор, которого не происходило.
- Убраны остатки лишней работы при экспорте и рендере. Рендер чата читает все месяцы через одно соединение с базой вместо нового на каждый месяц: открытие стоит обращения к файлу, чтения схемы и холодного кэша страниц, а прагмы (`cache_size`, `mmap_size`, `temp_store`) задаются соединению, не базе, — у чата с сотнями месяцев ни одно из них не успевало ничего накопить. Пути к медиафайлам приводятся к относительным по паре значений, вычисленной один раз на чат: `Path.cwd()` и `Path.resolve()` вызывались на каждое сообщение. Число сообщений чата пересчитывается в конце прогона только если сообщения действительно добавились — COUNT(*) линеен по размеру чата, а инкрементальный прогон чаще всего не пишет ничего. Сводка `state show` собирается одним проходом (LEFT JOIN с группировкой) вместо коррелированного COUNT(*) на каждую строку.
- CLI разложен на пакет `tg_export/cli/`: модуль на группу команд (`auth`, `account`, `takeout`, `tg`, `state`) плюс `export` для команд вокруг экспорта и `common` для общего пролога; `__init__.py` собирает группы в `main` и остаётся точкой входа `tg-export`. Прежде весь интерфейс жил в одном файле на две тысячи строк -- вдвое крупнее следующего модуля, -- и часть отложенных импортов существовала именно из-за его размера. Единственный `Console` вывода перенесён из `exporter.py` в `tg_export/console.py`: команда `tg send`, не имеющая отношения к экспорту, тянула ради прогресса отправки весь модуль экспортёра.
- Решение «чем закончить команду» собрано в одном месте. Константы кодов возврата переехали в `tg_export.errors` к иерархии доменных ошибок, у `TgExportError` появился атрибут `exit_code`, и точка входа берёт код из класса ошибки, а не подставляет единицу всей иерархии. Шестнадцать мест выхода сведены к одному помощнику, который печатает отказ и завершает команду через документированный `ctx.exit()`; прежде там стоял `click.exceptions.Exit`, не вынесенный в публичное пространство имён click.
- Предположения о Telethon закреплены тестами. Конвертер ветвится по именам классов (`__class__.__name__`), поэтому переименование класса в библиотеке не давало ни ошибки импорта, ни ошибки типизации -- разбор молча уходил в ветку `unknown`; теперь каждое такое имя сверяется с `telethon.tl.types`. Обход дефекта порядка колонок в файле сессии читает и пишет позиции, поэтому состав и порядок колонок `sessions` и версия схемы тоже проверяются. Шаблон поиска медиа в экспорте Telegram Desktop собирался из множества, и порядок альтернатив зависел от рандомизации хэша строк -- заменён на кортеж.

### Исправлено

- Перекачивание битого файла идёт под той же политикой повторов, что и выгрузка: преходящий отказ (обрыв связи, таймаут, ответ сервера об ожидании) повторяется с экспоненциальной паузой, а отказ, который повтор не изменит (нет места, нет прав, файловая система только для чтения), не повторяется вовсе. Прежде проверка целостности вызывала транспорт напрямую, и первый же обрыв связи оставлял файл битым -- то есть проход, задача которого восстановить файлы, завершался отказом там, где достаточно было повторить попытку.
- Отказ фазы проверки больше не уносит итог прогона. Отказ базы или сети вокруг перекачивания выходил из `run` целиком: сводка не печаталась, индексная страница не создавалась, накопленный список ошибок терялся, и многочасовой экспорт, уже записанный на диск, выглядел как полностью упавшая команда. Теперь отказ фазы записывается в ошибки прогона, как это делает соседняя фаза общих данных.
- Исход перекачивания разбирается по перечислению, а не по признаку «не пусто»: исход, добавленный в перечисление и не разобранный в месте показа, засчитывался в перекачанные и отчитывался как починенный файл. Код возврата команды `verify` закреплён тестом: файл, оставшийся битым, даёт `1`.
- Пример конфигурации в README загружается: у правила чата стоял ключ `action: skip`, которого загрузчик не знает -- он принимает `skip: true`, -- а неизвестный ключ отвергает файл целиком. Примеры из README и справочника теперь проходят тот же загрузчик, что и файл пользователя: и конфиг аккаунта, и глобальный `config.yaml`.
- Карта пакета в CONTRIBUTING называет `verify.py`: модуль появился, а таблица, объявленная в том же разделе актуальной картой, о нём умалчивала. Полнота таблицы и полнота индекса ADR закреплены тестами.
- Настройки `left_channels` и `archived` со значением `export_with_defaults` действительно выгружают такие чаты. Значение снимало запрет, но чат затем шёл через общий подбор правил и отсекался веткой `unmatched`, значение которой по умолчанию -- и в шаблоне, создаваемом `init`, -- равно `skip`: покинутые каналы и архив запрашивались у сервера, перечислялись в каталоге и не попадали ни в одну выгрузку. Теперь чат, уже допущенный одной из этих двух настроек, не проверяется правилом `unmatched` повторно.
- Медиа-настройки папки не перекрываются правилом типа чата. Документация и сам метод подбора объявляют приоритет `chats > folders.chats > folders > type_rules`, но правило типа проверялось раньше правила папки: канал в папке с `media: all` скачивался по настройкам `type_rules.channels`. Правило типа со значением `skip` по-прежнему действует внутри папки -- оно запрещает чат, а не описывает его медиа.
- Булевы настройки общих данных (`personal_info`, `contacts`, `sessions`, `userpics`, `stories`, `profile_music`, `other_data`) проверяются на тип, как и остальные разделы конфигурации. Запись `personal_info: "false"` -- строка, а непустая строка в Python истинна, -- включала то, что пользователь выключал.
- `parse_size` отвергает значения, которые не могут быть размером: `max_file_size: true` превращался в один байт, то есть в запрет скачивать что-либо, а отрицательное число давало тот же запрет с другой стороны. Оба случая проходили без сообщения, потому что `bool` в Python -- целое число.
- Пароль прокси не попадает в `config --json`: секция уходила в машиночитаемый вывод сырой, тогда как в тексте той же команды пароль всегда был скрыт как `***`, а `api_hash` исключён намеренно. В JSON остаются тип, хост, порт, `rdns`, имя пользователя и признак `password_set`. Сообщение об ошибке разбора секции больше не приводит её значение целиком — прокси, записанный одной строкой, нёс бы пароль в терминал и журнал.
- Перекачивание битого файла выбирает имя назначения через тот же реестр, что и выгрузка. Замена скачивается во временный каталог, где ничего нет, поэтому Telegram в каждой корутине отвечает базовым именем: два файла, которые экспорт развёл как `photo.jpg` и `photo (1).jpg`, переносились на один путь, второй перенос затирал первый, а уцелевшая запись в базе получала чужой размер. Теперь имя закрепляется за перекачиванием так же, как за загрузкой, причём за ним остаётся его собственный прежний файл -- перекачивание больше не переименовывает файл на каждом проходе, -- а прежний файл под другим именем удаляется только тогда, когда его имя никем не занято.
- Запись о скачанном файле доходит до базы, даже если загрузку отменили в этот момент. Файл к тому времени уже лежит на месте, а конвейер загрузок штатно снимает задачи, оставшиеся в полёте: защита стояла только на коммите, поэтому отмена, пришедшая в сам INSERT, оставляла файл на диске без строки в `files` -- следующий прогон удалял его как осиротевший и скачивал заново. Теперь вставка и коммит выполняются одним защищённым шагом.
- `tg download` сравнивает скачанное только с тем, что скачал сам. Набор для отсева дублей собирался из всего содержимого выходного каталога -- а он по умолчанию текущий, -- и включал только что записанный `<msg_id>.txt`: посторонний файл того же размера с теми же первыми 64 КБ приводил к удалению скачанного медиа без единой строки об этом.
- `account list` не показывает промежуточный файл входа как аккаунт. Вход пишет в `.<alias>.session.new.session` и подменяет рабочий файл только после успеха, а отбор шёл по суффиксу `.session`: процесс, убитый посреди входа, оставлял запись, которую перечисление показывало аккаунтом, а `auth check` пытался открыть.
- Снимок идущих загрузок стал копией значений, а не ссылок. Записи прогресса правились по полям из цикла событий, тогда как поток отрисовки читал их вне замка: в один кадр попадали объём принятого от нового вызова колбэка и общий размер, ещё равный нулю, -- rich получал `completed` без `total` и перерисовывал полосу назад. Запись прогресса теперь неизменяема и публикуется целиком на каждое обновление.
- Один кадр живого статуса собирается по одному снимку текущего чата. Полоса прогресса и обе строки состояния брали снимок каждая, и при смене чата между ними в кадре оказывались полоса нового чата и счётчики предыдущего -- та самая рассогласованность, ради которой снимок и заведён.
- Повторная отмена во время ожидания защищённой записи больше не срывает это ожидание. Удержание вызывающего до конца commit держалось на незащищённом `await`: второе нажатие Ctrl+C приходило прямо в него, вызывающий уходил закрывать соединение, и commit падал с `ValueError: Connection closed` в задаче, которую никто не ждёт. Отмена не теряется -- она поднимается после того, как запись завершена.
- Прогресс чата в `export_state` больше не откатывается записью из копии, снятой в начале обхода. Защита от отката стояла только на `last_msg_id`, а отметка спуска вниз по истории (`oldest_msg_id`) и признак дочитанного чата (`full_history`) писались присваиванием: второй процесс, которого не остановила advisory-блокировка -- её нет там, где нет `fcntl`, и она не действует между машинами на сетевом хранилище, -- поднимал отметку наверх и снимал признак, после чего пропуск в истории оставался навсегда, потому что фаза 2 для такого чата больше не запускалась. Теперь отметка спуска только убывает (ноль означает «ещё не спускались» и минимум не выигрывает), признак дочитанного только включается, а осознанный откат остаётся за `state reset`.
- Загрузка не повторяется на отказах, которые повтор не меняет. `OSError` целиком считался преходящей ошибкой, поэтому «нет места», «нет прав», «файловая система только для чтения», «слишком длинное имя» и превышение квоты проходили три попытки с ожиданием 2**attempt секунд каждая: исчерпание места превращалось в долгий холостой проход по всему каталогу. Такие коды теперь доходят до вызывающего с первой попытки.
- Отмена во время открытия базы состояния освобождает блокировку и закрывает соединение. Перехватывался `Exception`, а второй Ctrl+C приходит как `CancelledError` (наследник `BaseException`): отмена между захватом блокировки и концом открытия оставляла блокировку взятой, а соединение -- открытым, причём `__aenter__` не завершался, поэтому закрыть его было уже некому и поток aiosqlite жил до конца процесса. Закрытие базы, в свою очередь, освобождает блокировку даже при своём отказе.
- Отказы на путях освобождения ресурсов и переиспользования файлов записываются в журнал. Прежде молча гасились: отказ закрытия базы (например, при сбросе WAL) -- пользователь читал «Export complete» и код 0; отказ освобождения takeout-контекста, у которого есть последствие на сервере; неудачная ссылка или копия уже скачанного файла, из-за чего вместо переиспользования шла полная загрузка; нечитаемый заголовок выгрузки Telegram Desktop, из-за которого чат просто не попадал в индекс импорта.
- Конфигурация аккаунта попала под ту же защиту прав, что и остальные файлы каталога настроек. `init` дописывает в неё по строке на каждый чат -- идентификатор, имя и число сообщений, то есть полный список контактов, групп и каналов, -- а файл создавался с правами по umask, и при чтении его режим не проверялся, в отличие от `config.yaml` с паролем прокси. Теперь шаблон пишется сразу приватным, а конфиг, доставшийся от прежней версии или написанный руками, ужимается при чтении с записью в журнал.
- Нижняя граница `setuptools` в `[build-system]` поднята с 68.0 до 83.0.0. Прежняя граница допускала версии с тремя записями в OSV: внедрение команды через URL пакета и запись файлов за пределы каталога (обе HIGH), а также обход исключений `MANIFEST.in` при сборке sdist -- последнее относится напрямую к этому проекту, поскольку дистрибутив собирается из рабочего дерева, где рядом лежат выгрузка и файлы покрытия. Границы `jinja2` и `click` были подняты по такому же поводу.
- Путь к базе состояния кодируется при подстановке в SQLite-URI и в потоковом рендере, а не только при обращении к соседней базе. Символ `?` в пути (каталог экспорта задаёт пользователь) начинал строку параметров и отбрасывал `mode=ro` вместе с остатком пути: SQLite открывал другой, пустой файл и притом на запись -- рендер получал пустую базу, а рядом с пишущим соединением появлялась посторонняя ручка. Читающее соединение дополнительно выставляет `PRAGMA query_only`, чтобы гарантия не зависела от разбора строки.
- Файлы с секретами создаются приватными, а не ужимаются вторым шагом. `api_credentials.yaml`, файл сессии с ключом авторизации и база состояния создавались с правами по umask (обычно доступными на чтение всем), и `chmod 0600` шёл следом: в этом окне другой локальный пользователь успевал открыть дескриптор, который сохраняет доступ и после смены прав. Теперь файл открывается сразу с режимом 0600, а библиотеке (Telethon, SQLite) передаётся уже существующий приватный файл. Отказ `chmod` больше не проглатывается молча -- он попадает в журнал предупреждением.
- Папки, заданные флагами фильтра (`contacts`, `groups`, `broadcasts`, `bots`), применяются и к архивным чатам. Присвоение шло до того, как в каталог добавлялись архивные диалоги, поэтому архивный чат получал папку только при явном перечислении в фильтре. Папка участвует не только в раскладке каталогов: по ней подбирается правило `folders.<имя>`, и при `archived.action: export_with_defaults` архивный чат выгружался по другим настройкам, чем такой же неархивный.
- `purge` сообщает отказ базы, а не выдаёт его за отсутствующий чат. Разбор числового идентификатора и запрос к каталогу делили один `except ValueError`, а `ValueError` возбуждает и aiosqlite при закрытом соединении: такая ошибка уводила выполнение в поиск по имени с аргументом-числом и заканчивалась сообщением «No chats found matching '<id>'».
- `state reset --delete-messages` обнуляет и записанное число сообщений. Сообщения удалялись, а колонка `messages_count` сохраняла прежнее значение, и строка чата оставалась внутренне противоречивой: индексная страница берёт записанное число в обход фактического `COUNT(*)`, поэтому чат с пустой таблицей продолжал объявлять прежние тысячи сообщений.
- Чат, о котором известно, что выгруженных сообщений в нём нет, показывается нулём. Сводка по чатам пропускала нулевые значения, вызывающий не находил чат в словаре и подставлял `chat.messages_count` -- идентификатор последнего сообщения, который Telegram отдаёт вместо счётчика, поэтому пустой чат объявлялся на индексной странице числом в тысячах.
- Признак «история выгружена целиком» больше не выставляется проходом, остановленным границей `date_from`. Остановка по дате означает, что спуск закончил фильтр, а не чат: признак навсегда отключает вторую фазу, поэтому снятие границы в конфиге уже не возвращало сообщения старше неё -- помогал только `state reset`. Теперь признак записывается лишь после исчерпанного итератора.
- История, скачанная файлом без расширения, отрисовывается как фотография. Расширение проверялось вхождением суффикса в строку (`suffix in ext`), а пустая строка входит в любую: файл без расширения попадал в `<video>` вместо `<img>` и не показывался. То же касалось суффиксов `.m`, `.mo`, `.av`.
- Справка `--account` называет команду, которая существует. Одиннадцать объявлений опции описывали её двумя разными способами, и шесть из них отсылали к `auth default`: такой команды нет, аккаунт по умолчанию задаёт `account default`, и пользователь, следующий подсказке, получал `Error: No such command 'auth default'`. Текст задан одной константой, а тест разбирает справку всех команд и опций и роняет проверки, когда названное там имя команды не резолвится деревом CLI.
- `tg info` без идентификаторов и без `--from-catalog` завершается кодом 2 с блоком usage, а не нулём: ветка печатала подсказку и возвращала пустое значение, которое вызывающий читал как успех -- под `--quiet` команда молчала и всё равно сообщала об успешной работе. Фильтр `--from-catalog --type`, не подобравший ни одного чата, теперь печатает под `--json` пустой документ `[]` вместо пустого stdout, на котором `jq` падал с ошибкой разбора.
- Параллельность загрузок держится и в чате с редкими вложениями. Окно конвейера считалось по числу сообщений в очереди, а не по идущим загрузкам: текстовое сообщение заводило задачу и занимало место в окне, поэтому при вложениях реже, чем одно на `concurrent_downloads` сообщений, цикл стоял на ожидании самой старой задачи, а за ней в очереди ждали уже завершённые тексты -- и одновременно шла ровно одна загрузка. Замер на стенде при `concurrent_downloads: 4`: вложение у каждого 4-го сообщения давало пик 1, теперь 4. Сообщению без вложения задача больше не заводится вовсе.
- Отмена прогона больше не превращается в отказ одного чата. `CancelledError` гасилась при выгрузке чата и возвращалась как «этот чат не удался»: цикл выходил, флаг принудительной остановки оставался снятым, и сразу после просьбы остановиться запускалась фаза глобальных данных -- контакты, сессии, истории, аватары. Теперь отмена доходит до общего обработчика, который завершает прогон, а там, где она погашена намеренно, запрос снимается с задачи: иначе задача до конца жизни числится отменяемой, и любой объемлющий `asyncio.timeout` или `TaskGroup` (в том числе внутри Telethon) ведёт себя так, будто отмена ещё в пути.
- Два разных файла с одинаковым именем исходника больше не пишутся по одному пути. Загрузки сериализовались по `file_id`, а бороться им приходится за имя в каталоге назначения: Telegram массово отдаёт `photo.jpg` и `document.pdf`, поэтому две корутины видели место свободным одновременно, первая делала ссылку, вторая копировала поверх неё, и прогон заканчивался одним файлом на диске и двумя записями в состоянии, указывающими на него; проверка размера при этом удаляла файл, который сосед только что положил. Имя выдаётся общим реестром: занятое другим писателем не берётся, и все три пути переиспользования (соседний чат, соседний аккаунт, импорт из Telegram Desktop) вместе с перемещением завершённой загрузки пользуются им одинаково.
- Занятый другим процессом файл сессии сообщается, а не молча пропускается. Отказ «database is locked» при чтении состояния Takeout обрабатывался вместе с «такую форму таблицы читать нечем»: значение оставалось в колонках, а запуск шёл дальше -- в ту самую позиционную распаковку Telethon, из-за которой сохранённый `takeout_id` попадает в слот ключа и старт падает с `TypeError`. Теперь занятость отделена от прочих ошибок SQLite и завершает запуск с указанием пути, а остальные ошибки чтения записываются в журнал предупреждением, а не отладочным сообщением.
- `tg-export init` не перезаписывает существующую конфигурацию: команда завершается кодом 1 и называет путь, а перезапись запрашивается флагом `--force`, который сохраняет прежний файл рядом как `<имя>.bak`. Список чатов со временем меняется, поэтому повторный `init` ожидаем, а правила по папкам, лимиты и даты, написанные руками, восстановить неоткуда -- в отличие от сессии и каталога чатов.
- Опечатка в имени ключа внутри секции конфигурации сообщается, а не подменяется умолчанием. Прежде состав ключей сверялся только на верхнем уровне: `max_size` вместо `max_file_size` оставлял предел 100 МБ вместо заданных 10, `date_form` вместо `date_from` выгружал всю историю вместо среза, а `unmatched: export_with_defaults`, написанный скаляром, сводился к `skip` -- к действию, противоположному написанному. Правило чата без `id` и `name`, которое не могло совпасть ни с одним чатом, теперь отвергается при разборе.
- Учёт скачанного файла падал с `TypeError` на Python 3.11: исход загрузки проверялся на членство в перечислении, а такая проверка значения возвращает `bool` только начиная с 3.12. Версия 3.11 объявлена в `requires-python` и входит в матрицу CI.
- Экспорт останавливается, когда на диске кончилось место. Ошибка нехватки места перехватывалась наравне с отказом отдельного файла, поэтому ветка остановки не срабатывала: прогон шёл по всем оставшимся сообщениям, ничего не скачивая, и складывал в сводку по строке на каждое медиасообщение.
- Отказы фазы глобальных данных (личные данные, контакты, сессии, аватары, истории, рингтоны) попадают в сводку и в код возврата. Прежде они только писались в журнал, и прогон, не выгрузивший ни одного из этих разделов, завершался кодом 0 с сообщением «Export complete».
- Прерывание по Ctrl+C вне цикла экспорта завершает процесс кодом 130, а не 1 с сообщением «Aborted!». Click в standalone-режиме перехватывал прерывание сам, и обработчик точки входа до него не доходил.
- `run --verify` не удаляет повреждённый файл до того, как скачана замена. Команда `verify` была исправлена для этого раньше, но перекачивание было реализовано дважды, и правку получила только одна копия; теперь реализация одна.
- Чат, рендер которого был прерван, достраивается на следующем прогоне. Признаком готовности считался любой файл по маске `messages*.html`, под которую подпадают уже записанные помесячные страницы, поэтому месяцы после точки прерывания не появлялись, а ссылка с индексной страницы вела на несозданный `messages.html`.
- Строка состояния и главная полоса прогресса читают счётчики текущего чата одним согласованным снимком. `begin_chat` присваивал поля по одному, и поток обновления Live успевал прочитать число уже выгруженных сообщений нового чата рядом со снимком предыдущего: полоса показывала выполнено больше, чем всего. Начало чата теперь публикуется одним неизменяемым объектом, а чтение повторяется, если граница чата пришлась на его середину.
- Скорость в строке состояния считается по текущему чату, а не по всему прогону: числитель (байты и сообщения) сбрасывался на каждом чате, а знаменатель продолжал расти с начала запуска, и через час экспорта показанная скорость была занижена в десятки раз.
- Вторая фаза экспорта продолжается с того места, где остановилась первая. Прерывание между фазами оставляет нулевой `oldest_msg_id` при непустом `last_msg_id`, и обход шёл с самого свежего сообщения, то есть чат перебирался целиком заново.
- Проверка файлов сообщает о своих отказах, а не о всех накопленных за прогон: в итог `verify` попадала длина общего списка ошибок, включая ошибки скачивания предыдущих чатов.
- Пути переиспользования файлов (соседний чат того же аккаунта, выгрузка соседнего аккаунта, импорт из tdesktop) сверяют размер уже существующего файла, а не только совпадение имени. Обрыв прошлого прогона оставляет обрезанный файл под тем же именем, и он возвращался как готовый и регистрировался в состоянии со статусом `done`; теперь такой остаток заменяется.
- Покинутые каналы читаются постранично. `GetLeftChannelsRequest` вызывался ровно один раз с `offset=0`, и при числе покинутых каналов больше страницы остальные не попадали в каталог и не обрабатывались правилом `left_channels_action` -- без признаков в журнале.
- Команда `state reset` отличает не переданный идентификатор чата от нулевого: проверка `not chat_id` трактовала `0` как «не задан».
- Возможности, описанные в документации, но не работавшие в коде, приведены в соответствие. `tg-export init --from <каталог>` действительно записывает конфигурацию: прежде команда читала YAML, отбрасывала результат разбора и печатала «Config saved», не создав файла, а следующая команда сообщала «Config not found». Каталог читается и в форме YAML с разделами `folders`/`unfiled`/`archived`/`left`, и в плоской форме JSON; повреждённый файл сообщается как ошибка конфигурации, а не трассировкой. Настройка `defaults.export_service_messages: false` перестала игнорироваться -- служебные сообщения (вход в группу, смена названия, закрепление) больше не попадают в выгрузку, при этом указатели обхода продвигаются и по пропущенным сообщениям, так что повторный запуск не перечитывает их заново. Страница «Прочее» со списком рингтонов управляется одним флагом `profile_music`; ключ `other_data` зарезервирован и это указано в документации. Из допустимых значений убраны нереализованные: `output.format` принимает только `html` (значения `json` и `both` не были реализованы ни в одном пути рендера), `unmatched.action` -- только `skip` и `export_with_defaults` (значение `ask` нигде не обрабатывалось и вело себя как `skip`).
- Ошибки экспорта стали наблюдаемыми. Сбой отдельного файла теперь пишется в лог с идентификаторами чата и сообщения и с трассировкой, а не только увеличивает счётчик: прежде «Errors: 137» не поддавалось расследованию ни при каком уровне логирования, потому что исключение не доходило до logging. Итоговая сводка печатает первые десять ошибок и число оставшихся, а не одну цифру. Строка о сбое чата называет тип исключения -- у `TimeoutError` и `ValueError` пустой текст, и сообщение обрывалось на двоеточии. Повторы загрузки перестали быть бесшумными: каждая неудачная попытка пишется на DEBUG с типом ошибки и задержкой, исчерпание попыток -- на WARNING. Ошибки Telegram RPC (`ServerError`, `TimedOutError`) считаются временными и повторяются наравне с сетевыми: они наследуются от `RPCError`, а не от `OSError`, и потому не ретраились вовсе; `FloodWaitError` выжидает объявленное сервером время, а при задержке дольше пяти минут файл отмечается неудачным, не задерживая экспорт. Неудачи выгрузки аватаров, историй и рингтонов считаются и показываются рядом с числом сохранённых (`exported: 10 profile photos, 50 failed`) -- счётчик успеха без счётчика неудач создавал видимость полноты. Тихие переходы к запасному варианту получили запись в журнале: недоступный список покинутых каналов и недоступные частые контакты теперь сообщаются на WARNING, поскольку меняют состав выгрузки.
- Непредвиденная ошибка (Telethon, sqlite, сеть) выводится строкой `Error: <тип>: <текст>` с подсказкой про `--debug`, а не полной трассировкой поверх незакрытого прогресс-бара.
- Ветка двухфакторного входа выбирается по типу исключения Telethon (`SessionPasswordNeededError`, `PasswordHashInvalidError`), а не по подстроке в имени класса. Прежний разбор ломался бы молча при переименовании класса в Telethon: вместо запроса пароля пользователь получил бы трассировку. Заодно посторонняя ошибка входа больше не проходит через ту же ветку -- она распространяется сама, без `else: raise`. Статусные строки логина переведены в stderr: stdout зарезервирован под машиночитаемый вывод команд.
- Неудачный вход больше не оставляет аккаунт без сессии. `auth add` теперь логинится в отдельный файл и занимает штатный путь сессии только после успешного `get_me()`; прежде рабочий файл удалялся до входа, и неверный код, обрыв связи или Ctrl+C на приглашении лишали пользователя и старой сессии, и новой -- восстановить её можно было только повторным полным входом с кодом из Telegram. Соединение закрывается на любом пути выхода, включая прерывание, а файлы неудачного входа убираются. Новый файл сессии сразу получает права `0600`.
- База состояния, созданная прежней версией, приводится к текущей схеме при открытии. Схема создавалась только через `CREATE TABLE IF NOT EXISTS`, а на существующем файле это ничего не меняет: колонка `is_archived`, добавленная в `catalog_cache`, не появлялась, и первая же запись каталога падала с `OperationalError: table catalog_cache has no column named is_archived` -- уже внутри запущенного экспорта. Теперь недостающие колонки добавляются `ALTER TABLE` по фактическому составу таблиц, а ожидаемый состав читается из того же объявления схемы, так что второй список поддерживать не нужно. В файл записывается версия схемы (`PRAGMA user_version`) -- опора для будущих изменений, которые добавлением колонки не решаются.
- Форматирование сообщений с эмодзи больше не теряется и не смещается. Telegram задаёт границы entity (жирный, курсив, ссылки, код) в кодовых единицах UTF-16, а разбор резал Python-строку по кодовым точкам: после первого же символа вне BMP -- любого цветного эмодзи, части иероглифов, музыкальных знаков -- все последующие границы сдвигались, и entity либо не проходила проверку границ и молча отбрасывалась вместе с разметкой, либо вырезала соседний фрагмент, из-за чего подпись ссылки переставала соответствовать её адресу. Разбор переведён на единицы UTF-16.
- `verify` больше не берётся за файлы, пропущенные намеренно. Отбор шёл по условию `status != 'done'`, которое смешивало «не докачано» и «пропущено по размеру или по типу»: команда пыталась перекачать ровно те файлы, которые конфигурация исключила. Заодно в отбор попадают строки с неизвестным размером: сравнение с `NULL` в SQLite даёт `NULL`, а не истину, поэтому такой файл не проверялся никогда.
- Служебные отметки времени в базе состояния (`updated_at`, `downloaded_at`) пишутся в UTC с явным смещением, как и даты сообщений: прежде одинаково объявленные колонки хранили значения двух форматов -- наивное локальное время и момент со смещением, -- что делало их несравнимыми при переносе базы между часовыми поясами. Строки, записанные прежними версиями, сохраняют локальное время.
- Ожидание блокировки базы задано явно (30 секунд) и одинаково для всех соединений: рабочего, read-only-чтения помесячных страниц и поиска файлов в базе соседнего аккаунта. Прежде первые два полагались на умолчание stdlib в 5 секунд, которое соседний код уже считал недостаточным -- на большом батче пишущий процесс удерживает блокировку секундами.
- Из настроек соединения убран `PRAGMA foreign_keys = ON`: внешних ключей в схеме нет, и прагма обозначала защиту, которой не существует. Связи между таблицами поддерживает приложение, что и указано в комментарии к схеме.
- Страницы чата не перерисовываются, когда чат не изменился. Прежде рендер шёл безусловно: все ранее собранные страницы удалялись и строились заново -- с загрузкой каждого месяца из SQLite и разбором JSON-полей каждого сообщения, -- даже если инкрементальный запуск не принёс ни сообщения, ни файла. Теперь рендер запускается, когда за прогон что-то записано либо когда страниц на диске нет.
- Индексная страница читает число сообщений одним запросом на все чаты вместо одного-двух запросов на каждый чат: у аккаунта с сотнями чатов это были сотни обращений к базе на построение одной страницы.
- Служебные запросы к таблице файлов перечисляют нужные колонки вместо `SELECT *`; они выполняются на каждый медиафайл, то есть в самом горячем пути экспорта. Поиск по сообщениям принимает `limit`: отбор по `LIKE '%...%'` индексом не поддерживается, и каждая найденная строка собирается в Message с разбором JSON-полей.
- Границы версий зависимостей приведены к проверенным: `jinja2>=3.1.6` (первый выпуск без пяти уязвимостей, затрагивающих 3.1.0-3.1.5), `click>=8.3.3` (исправлено внедрение команды в `click.edit()`, которую проект не вызывает), `telethon>=1.36,<2` (в Telethon v2 слой сессий переписан, и класса `SQLiteSession`, вокруг которого построен обход ошибки порядка колонок, там нет), `python-socks[asyncio]>=2.0,<3` (Telethon правит приватные внутренности этой библиотеки, а сочетание с вышедшей 3.0.0 не проверялось). В `uv.lock` версии и прежде были безопасными -- границы защищают тех, кто ставит пакет в готовое окружение.
- Конфигурация проверяется при загрузке, а не отказывает молча в середине экспорта. `concurrent_downloads` сверяется с документированным диапазоном 1-5: значение `0` уходило прямо в `asyncio.Semaphore` и подвешивало загрузку медиа без сообщения и без таймаута, строка в кавычках и отрицательное число давали `TypeError`/`ValueError` с трассировкой. `media.types` обязано быть списком известных типов: скаляр `types: photo` превращал проверку вхождения в поиск по подстроке, из-за чего при `types: video_note` скачивались и обычные видео, а опечатка `photos` просто отключала загрузку соответствующих файлов. Ключи `type_rules` сверяются с типами и категориями чатов, записи `import_existing` -- с наличием обоих полей и допустимым `type`. Даты сообщают, в каком поле ошибка, и значение неподходящего типа (`date_from: 2024` читается YAML как число) больше не теряется без предупреждения.
- Глобальный `config.yaml` проверяется наравне с остальными файлами. Опечатка в имени секции (`proxi:` вместо `proxy:`) или прокси, записанный строкой вместо словаря, приводили к подключению напрямую без единого сообщения -- то есть ровно к тому исходу, ради предотвращения которого запуск прерывается при отсутствии `python-socks`. Теперь неизвестный ключ, неверная структура секции и негодные `host`/`port` останавливают команду с объяснением, а неизвестный тип прокси сообщается как ошибка конфигурации, а не трассировкой.
- Синтаксическая ошибка YAML в конфиге аккаунта выводится строкой `Cannot parse <файл>: ...` вместо трассировки.
- `min_free_space: 0` действительно отключает проверку свободного места: значение по умолчанию подставлялось через `or`, поэтому ноль заменялся на 20 ГБ. Само значение по умолчанию объявлено один раз и больше не расходится с тем, что показывает `tg-export config`.
- `~` раскрывается в `output.path` и в `--output`. Прежде запись `path: ~/exports` создавала каталог с именем `~` в текущем рабочем каталоге, и весь экспорт уходил туда.
- Файлы конфигурации читаются в UTF-8, а не в кодировке локали. Имена папок и чатов на кириллице на системе с не-UTF-8 локалью приводили либо к отказу чтения, либо к искажению имён, из-за которого правила молча переставали срабатывать.
- Команда `verify` больше не удаляет битый файл до того, как получит замену. Файл скачивается во временный каталог рядом с целевым и переносится атомарным переименованием только после успеха; обрыв связи или Ctrl+C оставляет прежний файл на месте. Каталоги, оставшиеся от прерванного запуска, убираются при следующем. Команда возвращает `1`, если удалось перекачать не все файлы.
- Потеря `takeout_id` на файлах сессии с физическим порядком колонок `(..., auth_key, tmp_auth_key, takeout_id)`. Telethon пишет строку `sessions` позиционно, поэтому смысл несёт позиция, а не имя колонки; чтение по имени забирало чужие значения, признавало настоящий `takeout_id` мусором и стирало его на каждом запуске, из-за чего режим Takeout не переиспользовался. Чтение переведено на позиции, значение резервируется до обнуления и восстанавливается после, а вся операция идёт в одной транзакции `BEGIN IMMEDIATE`.
- Падение старта на файле сессии схемы `version = 7` с активным Takeout (`TypeError: object supporting the buffer API required`): такая схема больше не пропускается обходом.
- Jinja-шаблоны и статика (CSS, JS, иконки) теперь попадают в дистрибутив. Без `[tool.setuptools.package-data]` в колесо уходили только `*.py`, поэтому любой экспорт после `pip install tg-export` падал с `TemplateNotFound: 'index.html.j2'`; дефект действовал с версии 1.0.0. Smoke-тест перед публикацией больше не ограничивается `--version`: он компилирует все шаблоны установленного пакета и рендерит индексную страницу.
- Прерывание фазы 1 (Ctrl+C) больше не оставляет безвозвратно пропущенный интервал сообщений. Фаза 1 идёт от новых сообщений к старым, поэтому указатель `last_msg_id` продвигается только после её полного прохода; фаза 2 спускается от `oldest_msg_id` и в пропущенный интервал не заходила, так что потерянные сообщения не забирал никто.
- Указатель `last_msg_id` больше не откатывается назад: запись из копии, прочитанной в начале экспорта чата, не может уменьшить уже достигнутое значение. Сброс через `state reset` работает как прежде.
- Удалена вторая, неиспользуемая реализация разметки сообщения. Блок сообщения собирался и шаблонами Jinja, и конкатенацией строк на Python, причём реализации уже разошлись: в шаблонной у отметки времени есть всплывающая подсказка с полной датой, в ручной её не было, а порядок кнопок и реакций был обратным. Работал только шаблонный путь -- ручной вызывался лишь из тестов, поэтому правка «не того» экземпляра проходила проверки, не меняя вывод. Тесты рендера переведены на рабочий путь, где экранирование обеспечивается самим шаблонизатором.
- URL inline-кнопки в HTML-выгрузке проходит проверку схемы: `javascript:` в кнопке попадал в готовую страницу и выполнялся при нажатии. Шаблонный путь такую проверку делал, ручной -- нет. Текст реакции экранируется: это была единственная неэкранированная подстановка в модуле.
- Файлы с секретами и личными данными создаются доступными только владельцу: файл сессии Telegram с ключом авторизации (был `0644`), база состояния с текстами всех сообщений, телефонами и адресами сессий, каталог выгрузки. Ранее созданный пользователем каталог сохраняет свои права -- он мог быть открыт намеренно. Права `config.yaml` с логином и паролем прокси проверяются так же, как у `api_credentials.yaml`: слишком широкие сужаются с записью в журнал.
- Ввод `api_hash` при `auth credentials` скрывается: набранный в открытую, он остаётся в истории оболочки.
- Имя аккаунта проверяется перед подстановкой в путь файла сессии и конфигурации: разделитель пути или ссылка на родительский каталог в имени размещали и удаляли файлы за пределами каталога настроек.
- Путь к базе соседнего аккаунта экранируется при сборке SQLite-URI: символ `?` в пути превращал остаток в параметры и снимал режим «только чтение».
- Файл блокировки состояния больше не удаляется при освобождении. `flock` привязан к inode, а не к имени: удаление позволяло процессу, успевшему открыть файл, удерживать блокировку на осиротевшем inode, пока следующий создавал новый файл и брал блокировку на нём. Два экспорта работали с одной базой состояния, взаимно удаляя файлы при уборке и затирая указатели.
- Файл сессии Telegram защищён собственной блокировкой. Прежняя блокировка привязана к каталогу вывода, поэтому не мешала ни `tg send` рядом с идущим экспортом, ни второму экспорту с другим `--output`: обе команды работали с одной сессией, а Telethon отвечает на это порчей ключа авторизации в файле. Теперь вторая команда сообщает, что сессия занята.
- Принудительное завершение (второй Ctrl+C подряд) снимает только задачу экспорта. Раньше отменялись все задачи цикла событий, включая внутреннюю задачу `asyncio.shield`, то есть ровно ту защиту, ради которой shield и поставлен: запись пачки сообщений и удаление данных чата могли остаться применёнными наполовину.
- Защищённая запись удерживает вызывающего до своего конца. `asyncio.shield` защищает операцию, но не вызывающего: тот получал отмену немедленно, доходил до закрытия соединения, и идущий commit падал в неотловленной задаче с `ValueError: Connection closed`.
- Команда `run` освобождает файл блокировки состояния и соединение, если отказ случился между их захватом: раньше оба захватывались до блока, который их освобождает.
- Установка обработчиков сигналов не роняет экспорт на платформах, где она не поддерживается (Windows): там Ctrl+C приходит обычным прерыванием, которому команда и так сопоставляет код `130`.
- Блокирующие операции вынесены из потока цикла событий. Поиск файла в базе соседнего аккаунта открывал SQLite обычным `sqlite3` и мог ждать занятого писателя до 30 секунд; копирование файла из выгрузки tdesktop и запасная ветка связывания между чатами читали и писали файл целиком; страницы глобальных данных и индекс собирались шаблонизатором при живом соединении с Telegram. Всё это время не обслуживались ни соседние загрузки, ни соединение. Рендер чата так работал и раньше. Свободное место проверяется не на каждый файл, а не чаще раза в пять секунд; неудачная проверка не кешируется.
- Загрузки медиа внутри чата идут параллельно, как обещают настройка `concurrent_downloads` и документация. Раньше загрузка ожидалась прямо в теле цикла по сообщениям, поэтому одновременной оставалась ровно одна: между файлами вставлялся полный цикл «запрос -- ответ» к серверу Telegram, а пока файл скачивался, итератор не запрашивал следующую пачку сообщений. Мёртвыми при этом были и семафор, и пофайловые блокировки, и защита списка активных загрузок. Сообщение по-прежнему попадает в базу только после своей загрузки и в прежнем порядке: ожидается всегда самая старая из идущих загрузок.
- Уборка после неудачной загрузки удаляет только собственные недокачанные файлы. Раньше удалялось всё, что появилось в общем каталоге чата с момента снимка, снятого ещё до постановки в очередь загрузки, так что при одновременных загрузках сносились файлы, только что дописанные соседней. Каждая загрузка идёт в свой временный подкаталог и переносится на место готовой; каталоги, оставшиеся от прерванного запуска, убираются при первом обращении к целевому каталогу. При совпадении имён свободное имя подбирается так же, как это делал Telethon.
- Прогресс отправки (`tg send`) не рисуется, когда вывод не является терминалом: раньше проверялся только `--quiet`, и при перенаправлении в файл или конвейер туда попадали перерисовки бара. Экспорт делал такую проверку с самого начала.
- Прогресс альбома больше не уходит за 100%. Telethon режет альбом на группы по десять и передаёт в обратный вызов остаток списка (25, затем 15, затем 5), тогда как счётчик отправленного считается от начала альбома; это значение перетирало общее число файлов. Теперь общее число задаётся один раз и берётся из самого списка.
- Вид полосы прогресса одинаков в обоих режимах отправки: проценты показываются и при побайтовом счёте, и при альбомном, а размер и скорость добавляются к ним, когда счёт идёт по байтам. Раньше одна и та же команда выглядела по-разному в зависимости от числа файлов.
- Имя файла в прогрессе отправки (`tg send`) экранируется перед выводом. rich разбирает описание задачи как разметку, поэтому имя вида `[draft]report.txt` печаталось как `report.txt`: квадратные скобки съедались вместе с содержимым. Используется та же функция экранирования, что и в прогрессе загрузки при экспорте.
- Флаг `--quiet` больше не глушит причину отказа. Признак «существенное сообщение» проставлялся вручную у отдельных вызовов, и из 94 мест его имели 20, причём 17 из них -- строки итоговой сводки; в результате `--quiet tg send 123` печатал пустой вывод и возвращал `1`, а одно и то же сообщение `Config not found` было видно в `run` и терялось в `state show`, `state reset` и `verify`. Все сообщения, за которыми команда завершается ошибкой, выводятся через отдельную функцию и переживают `--quiet`; статическая проверка не даёт новому пути отказа снова оказаться подавленным. Команда `purge` под `--quiet` показывает описание удаляемого перед запросом подтверждения: вопрос без описания предмета ответить нельзя.
- Ограничение размера файла для Takeout-сессии считается по всем применимым правилам, а не только по `defaults.media`. Разделы `chats`, `type_rules` и `folders` задают собственный `max_file_size`, и значение выше умолчания урезалось самой сессией: Takeout несёт один лимит на всё время жизни. Теперь берётся максимум из умолчания и лимитов правил, которые действительно приводят к скачиванию (правила со `skip`, а также вложенные чаты пропущенной папки, в расчёт не идут).
- Диагностика состояния файла сессии различает три разных состояния вместо одной строки на все. Сообщение «Detected stale takeout_id/tmp_auth_key ... staging restore» печаталось при каждом запуске, включая полностью исправный: Telethon при `store_tmp_auth_key_on_disk = false` всегда пишет в `tmp_auth_key` пустое значение, поэтому признак «в строке что-то есть» был истинным всегда, а восстанавливать при этом было нечего. Теперь перенос настоящего `takeout_id` сообщается на уровне INFO с указанием значения, штатное пустое значение уходит в DEBUG и не создаёт лишней записи в резервной таблице, а предупреждение о непригодном значении называет источник (строка `sessions` или отложенная копия) и поясняет, чем разовая санация отличается от повреждения, возникающего снова на каждом запуске.
- Интерактивный логин (`account add`) открывает файл сессии через `FixedSQLiteSession`, а не по строковому пути. Строка заставляла Telethon построить обычный `SQLiteSession`, который адресует колонки таблицы `sessions` по имени, тогда как записываются они позиционно; логин оставался единственным писателем вне защиты и потому источником повторного повреждения файла.
- Отказ Takeout больше не поглощается широким `except Exception` -- обрабатываются только ошибки, которые действительно означают недоступность Takeout, а дефекты кода доходят до вызывающего.
