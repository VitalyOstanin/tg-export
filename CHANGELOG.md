## [Не выпущено]

### Ломающие изменения

- Поддержка прокси входит в состав пакета: `python-socks[asyncio]` переехал из набора `[proxy]` в основные зависимости. Нужен прокси или нет, решает файл конфигурации, а не тот, кто ставит пакет, и окружение без этой зависимости не может обслужить конфигурацию с прокси -- Telethon в такой ситуации молча игнорирует настройку и подключается напрямую, раскрывая реальный IP. Установка стала на один пакет (380 КБ, без транзитивных зависимостей на поддерживаемых версиях Python) тяжелее для тех, кто прокси не использует. Набор `[proxy]` сохранён пустым, поэтому `uv tool install 'tg-export[proxy]'` и `pip install 'tg-export[proxy]'` из прежних инструкций продолжают работать; верхняя граница `python-socks<3` теперь действует на любую установку.
- Коды возврата приведены к единому правилу: `0` — успех, `1` — команда сообщила об отказе, `2` — ошибка разбора аргументов, `128 + номер сигнала` — прерывание. Раньше кодом `0` завершались `account remove` с неизвестным именем, `auth check` с непригодным аккаунтом, `tg send` при недоставке, `tg download` для отсутствующего сообщения, `state reset` для чата без состояния, `tg info` с ошибками запроса, а также `run` с ошибками экспорта. Прерывание по Ctrl+C вне цикла экспорта теперь тоже даёт `130`, а не `0` или `1`. Таблица кодов добавлена в README.
- Неверная форма вызова завершается кодом `2` с блоком usage, а не кодом `1` без него: `run --require-takeout --no-takeout`, `tg send` без `--text` и `--file`, `state reset` без `chat_id` и без `--all`. Соседний случай в том же наборе -- `tg messages --truncate 5 --no-truncate` -- давал код `2` и подсказывал, как команду следовало вызвать, а эти три отказывали строкой без usage. Правило записано в CONTRIBUTING: форма вызова -- `click.UsageError`, состояние системы -- `_fail`.
- Экспорт аккаунта идёт в подкаталог с его alias: `output.path` -- базовый каталог, итоговый путь `{path}/{alias}/`, как и было описано в документации. Прежде alias в путь не добавлялся и попадал туда только потому, что шаблон, создаваемый `init`, зашивал его в само значение; конфиг, написанный руками по документации или оставленный со значением по умолчанию `./export_output`, давал двум аккаунтам один каталог, одну базу состояния и переиспользование чужих файлов при дедупликации. Уже сделанные выгрузки остаются на месте: alias не добавляется, если последний элемент пути совпадает с ним или если каталог уже содержит базу состояния. Опция `--output` по-прежнему задаёт каталог экспорта целиком.
- Каталог конфигурации подчиняется стандарту XDG Base Directory (`XDG_CONFIG_HOME`) и может быть задан напрямую переменной `TG_EXPORT_CONFIG_DIR`. Прежде путь `~/.config/tg-export` был зашит, и держать раздельные наборы аккаунтов, сессий и учётных данных было нечем: `--config` переопределяет только конфиг аккаунта.

### Обновление с 1.x

- Каталог конфигурации подчиняется стандарту XDG Base Directory: при заданной `XDG_CONFIG_HOME` аккаунты, сессии и `config.yaml` берутся из `$XDG_CONFIG_HOME/tg-export`, а не из `~/.config/tg-export`. Если переменная задана, перенесите каталог или назовите прежний путь явно -- `TG_EXPORT_CONFIG_DIR=~/.config/tg-export`. Без `XDG_CONFIG_HOME` расположение прежнее.
- Экспорт идёт в `{output.path}/{alias}/`. Уже сделанные выгрузки остаются на месте: alias не добавляется, если последний элемент пути совпадает с ним или каталог уже содержит базу состояния. Конфигурация, где alias в `output.path` не вписан, начнёт писать в подкаталог -- перенесите каталог или допишите alias в путь.
- Коды возврата изменились: отказ команды -- `1`, неверная форма вызова -- `2`, прерывание -- `128 + номер сигнала`. Скрипты, считавшие успехом `0` от `run`, `tg send`, `tg download`, `tg info`, `auth check`, `account remove` и `state reset`, нужно проверить -- таблица кодов приведена в README.
- Дополнение `[proxy]` больше не требуется: `python-socks[asyncio]` входит в основные зависимости. Прежние команды с `tg-export[proxy]` продолжают работать -- набор сохранён пустым.
- Опция `init --output` переименована в `--output-file`; прежнее написание принимается.
- Правила `media` у чата, типа и папки начинают действовать: конфигурация, в которой они заданы, изменит состав скачиваемого -- прежде во всех чатах применялся только `defaults.media`. Анимации при этом переходят из `videos/` в `gifs/`; уже скачанные файлы остаются на прежних местах.

### Добавлено

- Пауза, на которую Telegram останавливает экспорт (flood wait), видна при штатном запуске: в терминале -- обратным отсчётом в статусной строке (`waiting: 12s flood wait`), а когда живого статуса нет (вывод перенаправлен, задан `--quiet`) -- строкой журнала о начале ожидания.
- `tg download --json` печатает в stdout документ с путями сохранённого: имена файлов выбирает Telegram, а строки о них шли только в поток диагностики и под `--quiet` исчезали совсем. Это была единственная запросная команда, чей результат нельзя было прочитать программой.
- Уровень логирования читается из `TG_EXPORT_LOG_LEVEL` -- переменной с префиксом проекта. `LOG_LEVEL` принимается по-прежнему, но стоит ниже: имя не принадлежит ни одному инструменту, и значение, оставленное там другим (например, `verbose`), валило любую команду tg-export, причём сообщение называло `--log-level`, которого пользователь не передавал.
- `tg send --text-file PATH` читает текст сообщения из файла, а при значении `-` -- со стандартного ввода. Единственным способом задать текст была опция `--text`, то есть текст проходил через командную строку: её читает любой локальный пользователь, и она остаётся в истории оболочки.
- `--json` появился у `tg messages`, `config` и `account default` -- флаг машиночитаемого вывода теперь есть у всех запросных команд. У `tg messages` это массив объектов с полями `id`, `date`, `sender`, `text`, `media`, `action`: прежде вывод разбирался регулярным выражением по строкам, и первое же многострочное сообщение построчный разбор ломало; обрезка текста в этом режиме по умолчанию не применяется, а тип медиа и вид системного сообщения стоят отдельными полями, а не приписываются к тексту.
- `auth check` и `takeout clear` принимают аккаунт и опцией `--account`, а не только позиционным `NAME`. Остальные девять команд знают только опцию, поэтому обёртка, подставляющая `--account "$ALIAS"` во все вызовы, на этих двух отказывала. Прежнее позиционное написание принимается; указание двух разных имён сразу отвергается кодом `2` с блоком usage.
- `SECURITY.md`: поддерживаемые версии, приватный канал сообщения об уязвимости (private vulnerability reporting на GitHub) и перечень того, что нельзя прикладывать к сообщению. Форма заведения issue предлагает этот канал ссылкой, а предупреждение в шаблоне отчёта об ошибке дополнено `api_id`, `api_hash` и файлом сессии.
- Опция `run --rerender`: HTML пересобирается по всем чатам, включая те, в которых ничего не изменилось. Рендер неизменившегося чата пропускается -- иначе каждый запуск перечитывал всю базу и собирал страницы заново, -- и следствием было то, что после обновления шаблонов такие чаты оставались собранными прежней версией, а способа заставить пересборку не было.
- Опция `run --no-takeout`: Takeout не запрашивается вовсе, экспорт сразу идёт через обычный API. Прежде единственным способом обойтись без Takeout было дождаться отказа и положиться на автоматический переход; запрос при этом стоит обращения, на которое Telegram отвечает кулдауном до суток.
- В корне репозитория появился `config.example.yaml` — рабочий пример конфигурации со всеми разделами, который загружается как есть; прежде полные примеры жили только в `docs/configuration.md`. Шаблон, который печатает `tg-export init`, дополнен разделами `archived` и `import_existing`: они разбирались кодом и были описаны в документации, но в шаблоне — основном способе познакомиться с составом настроек — не упоминались.
- `-h` работает как синоним `--help` во всех командах и группах: прежде он завершался кодом 2 с сообщением «No such option: -h».
- У `state reset --all` появилось подтверждение и флаг `--yes`. Перед сбросом печатается число затрагиваемых строк по таблицам базы состояния; с `--delete-messages` команда выполняла `DELETE FROM messages` и `DELETE FROM files` по всей базе без показа объёма и без вопроса, а опечатка в команде обходилась повторной выгрузкой всего аккаунта.
- Команда `list` принимает `--json` -- краткая форма `--format json`, одинаковая с `account list`, `auth check`, `state show` и `tg info`.
- Инструкция по установке в README приведена в рабочее состояние. Примеры быстрого старта записаны без префикса `uv run`: пакету, установленному из PyPI, каталог проекта недоступен, и первая же команда завершалась ошибкой `Failed to spawn: tg-export`; для работы из исходников префикс объявлен отдельной оговоркой.
- Скрипт `scripts/check.sh` прогоняет весь набор проверок CI одной командой: `uv lock --check`, `ruff check`, `ruff format --check`, `pyright`, тесты с покрытием и границы покрытия по модулям; `scripts/check.sh --fix` предварительно исправляет исправимое (`ruff check --fix`, `ruff format`).
- Релиз проверяется до необратимой публикации. Перед сборкой `publish.yml` прогоняет тот же набор проверок, что и CI на master (`scripts/check.sh`: синхронизация `uv.lock`, линтер, формат, типы, тесты, границы покрытия) -- прежде на релизном пути был только `pytest`, а `ci.yml` на push тега не срабатывает, поэтому тег на коммите с рассинхронизированным `uv.lock` или с ошибками типов публиковался беспрепятственно.
- Команда `tg info` принимает `--json`: результат по всем чатам выводится в stdout одним документом, как у `account list`, `auth check` и `state show`. Прежде машиночитаемый результат можно было получить только записью в файл (`--output`), в конвейер он не отдавался.
- Справочник команд `docs/cli.md`: назначение, опции, поведение и коды возврата всех девятнадцати команд. Прежде документация проводила пользователя только по девяти из них, а `config`, `verify`, `takeout clear`, `tg send`, `tg download`, `state show`, `state reset`, `account list`, `account remove` и `auth check` не были описаны нигде, кроме `--help`.
- Опция `run --require-takeout`: отказ Takeout завершает команду ошибкой вместо перехода на обычный API. Без флага поведение прежнее -- переход выполняется, но теперь он объявляется как существенное сообщение (видно и под `--quiet`), а использованный режим печатается в итоговой сводке строкой `API:`.
- Команда `tg send` принимает `--as-document`: файл отправляется без сжатия, как документ.
- Прогресс отправки файлов в `tg send`.

### Изменено

- Путь загрузки не делает файловых вызовов в потоке цикла событий: создание каталогов, уборка staging после убитого прогона и создание временного каталога вынесены в поток -- прежде каждый файл платил тремя обращениями к файловой системе, останавливая соседние загрузки того же чата. Правило закреплено тестом (проверено на нарушающем коде).
- Уборка staging проверяет имя записи прежде типа: на каталоге в двадцать тысяч файлов это двадцать тысяч вызовов `stat` против нуля.
- Рингтоны скачиваются через то же окно параллелизма, что фотографии профиля и истории: это был последний раздел общих данных, который просил файл, ждал его и только потом просил следующий.
- Параметры пакета сообщений собираются в потоке: сериализация пятисот сообщений занимает около шестнадцати миллисекунд, в течение которых на цикле не двигалась ни одна загрузка.
- Возвращаемый тип объявлен у каждой функции пакета: 136 из 483 обходились без него, причём деление шло не по слоям -- соседние функции одного модуля различались. Правило закреплено линтером (`ANN2`); на тесты и скрипты оно не распространяется.
- Шесть страниц общих данных собираются одним помощником: они различаются шаблоном, именем файла, заголовком и содержимым, а остальное -- пути к таблице стилей и сценарию, ссылка назад и запись файла -- было выписано в каждой. Сами пути объявлены константами `CSS_PATH` и `JS_PATH` вместо десяти литералов.
- Пределы разрастания поставлены и на модуль, и на класс (2100 строк и 75 методов): предел стоял только на функции, и `exporter.py` дорос до двух тысяч строк при формально нормальных функциях.
- Мелкое: `hasattr(x, "a") and x.a` сведено к `getattr(x, "a", None)`, помощник `forget_cancellation` перестал быть приватным именем чужого модуля, предел длины имени файла объявлен константой вместо двух литералов, гейт покрытия называет допуск из константы, а не словами рядом с ней. Убраны комментарии, пересказывающие следующую строку.
- Тесты строят `Chat` и `Message` фабриками `make_chat` и `make_message` из `conftest.py`: полный список полей был выписан двадцать один раз в одиннадцати файлах, и правка модели означала обход всех копий. Тест называет только то, что проверяет.
- `publish.yml` в тестах релиза читается одним способом -- помощником `tests/parity.py`, а не двумя.
- Исключения проверки языка артефактов сузились с файлов до строк: файл целиком выводился из-под проверки ради одной-двух строк с названиями разделов, и русский текст, добавленный туда позже, проходил молча.
- Разбор `scripts/check.sh` в сверке с CI считает вложенные `if` и не спотыкается о `timeout` перед командой; `uv run python` без аргументов больше не роняет разбор.
- Конвертер сообщений покрыт тестами по веткам: 62 % против 88 % теперь. Раньше не выполнялись ни разу разбор фотографии по вариантам размера, разбор опроса, ответы, пересылки, ряды кнопок и вся классификация документа -- то есть ветки, в одной из которых `gif` оказался недостижим.
- Контракт `--json` («в stdout только JSON») проверен у всех девяти команд, которые его обещают: добавлены `account list`, `auth check`, `state show` и `tg download`.
- Пример конфигурации из документации проверяется по результату загрузки, а не по отсутствию исключения: раньше это был единственный тест без утверждения.
- У локального прогона появился общий потолок времени (15 минут, как у задания CI): `pytest-timeout` ограничивает отдельный тест, но не прогон, который встал между тестами.
- Выражения, размноженные по модулям, сведены к общим помощникам. Имя пользователя «first + last» было выписано в пяти местах, причём копии уже разошлись в том, что подставляют вместо отсутствующего имени; извлечение числового идентификатора из объекта `Peer*` -- в пяти, из них две с другим порядком ветвей.
- Один вопрос -- один ответ в коде конвертера и экспортёра. Выбор конструктора по имени класса Telethon везде сделан таблицей: цепочка из восьми `if cls_name == ...` для медиа и `if/elif` для трёх видов реакций стояли рядом с таблицами, которые в комментариях объявлены заменой именно таким цепочкам.
- `config` показывает прокси так, как его читает экспорт, а не как записано в файле: опечатка в имени ключа давала порт `None` в выводе команды и подстановку умолчания при выгрузке, а прокси, записанный одной строкой вместо секции, завершал команду трассировкой `AttributeError`.
- `purge` отчитывается об удалённом в той же форме, в какой предупреждал: `Deleted from DB: messages=7, files=3, ...` вместо представления словаря Python со скобками и кавычками — пользователь сравнивает «сколько собирались удалить» и «сколько удалили» без пересчёта.
- `account default` печатает в stdout только само имя аккаунта, пояснение уходит в stderr. Прежде туда шла строка `Default account: <alias>`, а при незаданном аккаунте -- `No default account set.`, поэтому `NAME=$(tg-export account default)` получал пояснение как значение.
- Гейт релиза сверяет дату раздела `CHANGELOG.md` с датой коммита, на который указывает тег (допуск -- сутки на часовые пояса и на разрыв между подготовкой и пушем).
- Скрипт гейта без `--output` печатает release notes в stdout и файла не создаёт. Прежде умолчанием был `release_notes.md` в текущем каталоге, а `.gitignore` его не знал: локальная проверка гейта без флага оставляла файл в корне рабочего дерева, откуда его забирал `git add -A` релизного коммита.

- Вопросы пользователю печатаются в поток диагностики, а не в stdout. `click.confirm` и `click.prompt` по умолчанию пишут приглашение в stdout, поэтому у `purge chat > /dev/null` описание удаляемого уходило на терминал, а сам вопрос -- в перенаправление: процесс молча ждал ответа и выглядел зависшим, а stdout переставал быть пустым и получал прозу вместе с эхом ответа.
- Временные каталоги загрузки описаны одним правилом. Приём «качать рядом с целью и переносить готовое» был написан дважды, со своим префиксом у каждого: остаток убитого `run --verify` не удалял ни один обычный прогон, а `verify` не убирал остатки убитой загрузки.
- Убрана константа `FILE_STATUSES`, которую не читали ни пакет, ни тесты, ни скрипты, и записано ограничение, стоявшее за выбором `vars()` вместо `asdict()` при записи сообщения: `vars()` не обходит вложенные объекты, поэтому поле-dataclass в `TextPart`, `ForwardInfo`, `Reaction` или `InlineButton` сломало бы запись.
- Форматирование вывода собрано по одному описанию на каждую вещь. Таблица `state show` строится из перечня колонок: ширины были выписаны в двух форматных строках, а длина линейки под шапкой -- третьим, несвязанным числом 80, которое не совпадало ни с шапкой (62 знака), ни со строкой данных (77).
- Подчёркивание в именах снова означает «внутреннее». Модуль общих помощников `cli/common.py` существует ради того, чтобы его читали остальные группы команд, но почти всё, что он отдавал, было названо как внутреннее -- 119 обращений вида `common._имя` при публичных константах в том же файле.

### Исправлено

- Отзыв сессии прерывает прогон, а не считается отказом одного чата: каталог из сотен чатов проходился целиком, собирая одну и ту же ошибку про негодную сессию.
- Настроенный прокси без `python-socks` отвергается ошибкой конфигурации, а не голым `RuntimeError`: сообщение выходило с приставкой «RuntimeError:» и советом про `--debug` вместо одной строки по существу.
- Секция `proxy` проверяется на состав и типы: `user:` вместо `username:` давало подключение без учётных данных, а `rdns` и пароль принимались любого типа.
- `min_free_space` разбирается до подключения и до запроса Takeout: ошибка в значении обнаруживалась после запроса, который стоит кулдауна до суток.
- Отказ обеих попыток `du` объясняется в отладочном журнале, а не просто убирает строку размера; отказы необязательных загрузок (фото профиля, истории, рингтоны) отмечаются предупреждением, как соседние необязательные разделы.
- Удаление аккаунта уносит и попутные файлы базы сессии (`-wal`, `-shm`), а не только `.session` и `-journal`: в них лежат ещё не слитые страницы, то есть материал ключа авторизации -- он оставался на диске после явного удаления.
- Отказ ужать права каталога с сессиями и учётными данными объявляется предупреждением, а не гасится и не уходит в отладочный журнал: для файла тот же отказ уже был событием.
- Ссылка вида `/\host\share` и `\/host/share` в HTML отбрасывается наравне с `//host/share`: для схемы `file:` браузер читает прямой и обратный слэш одинаково, и смешанная пара вела на тот же удалённый адрес.
- Псевдоним аккаунта проверяется и на пути к каталогу выгрузки: имена файлов сессии и конфигурации проверялись, а этот путь -- нет.
- `.gitignore` закрывает `config.yaml` с логином и паролем прокси и попутные файлы сессий.
- Отсчёт паузы не исчезает с экрана раньше самой паузы: запись, которой владеет незакрытый блок ожидания, снималась с доски по расчётному сроку, хотя сон может идти дольше оценки -- как раз на загруженном цикле событий. По сроку теперь снимаются только сны, о пробуждении из которых никто не сообщает (пауза внутри telethon).
- Вложенный вход в блок «паузы видны на экране» не снимает признак у внешнего: признак стал счётчиком и читается под тем же замком, что и сама доска.
- `tg info --output-file` называет чат, который не удалось опросить: строка об отказе печаталась только без `--output-file`, поэтому команда завершалась кодом `1` без единого слова о причине, а под `--quiet` не выводила ничего. Отказавшие чаты считаются отдельно от сохранённых -- «Saved 2 entries» включало запись об отказе.
- `--quiet` глушит и строку прогресса обхода сообщений: соседняя строка по чатам молчала, а эта продолжала печататься.
- Текст сообщений и названия чатов очищаются от управляющих символов перед выводом в терминал: их задаёт Telegram, а терминал исполняет escape-последовательности как команды. Машиночитаемый вывод не затронут -- он отдаёт текст как есть.
- `--limit`/`-n` у `tg messages` и `tg info` отвергают отрицательное число вместо того, чтобы передавать его в запрос.
- `state reset --all CHAT_ID` отвергается кодом `2` с блоком usage: идентификатор молча отбрасывался, и сбрасывался весь аккаунт. Расхождение кодов возврата `state show` и `state reset` на чате без состояния описано в справочнике команд.
- Документация о приоритете правил называет исключение: правило типа с `skip: true` действует и внутри папки, то есть запрещает чат раньше, чем папка успевает описать его медиа. Прежде порядок был записан списком без этого случая, а сам случай -- только в CHANGELOG.
- Переменная `TG_EXPORT_LOG_LEVEL` названа во всех четырёх местах, где описан выбор уровня журнала (README, справочник команд, справочник конфигурации, строка помощи `--log-level`): три из них называли прежнюю цепочку с одним `LOG_LEVEL`, а две одноимённые таблицы «Порядок разрешения» отвечали по-разному. Согласованность закреплена тестом.
- В таблицу кодов возврата README добавлен `141` -- закрытый конвейер (`tg-export list | head`) завершает команду сигналом SIGPIPE.
- Поведение при нехватке места описано так, как работает: экспорт завершается ошибкой с сохранённым состоянием, а не «приостанавливается» в ожидании свободного места.
- Модель прав доступа (`0600` у файлов, `0700` у каталогов, ужатие прав вручную написанного конфига с предупреждением) описана в `SECURITY.md`; прежде она была только в коде и в CHANGELOG.
- Раздел `media` чата, типа и папки действует при скачивании. Он разбирался, проверялся и показывался `config -v`, но загрузчик создавался один раз с `defaults.media`, и каждый чат качался по умолчанию -- настройка не влияла ни на состав типов, ни на предел размера.
- Анимации (gif) снова распознаются как `gif` и попадают в каталог `gifs/`: ветка видео стояла выше, а gif в Telegram -- mp4 с обоими атрибутами, поэтому `media.types: [gif]` не скачивал ни одной анимации, а `[video]` скачивал их вместе с видео.
- Папка Telegram, отобранная по флагу «не контакты», больше не забирает контакты (и наоборот): оба флага давали одно и то же множество личных чатов, тогда как различие есть только в адресной книге -- она и запрашивается.
- `skip` у чата, типа и папки, а также `defaults.export_service_messages` проверяются на тип: `skip: "false"` в кавычках -- непустая строка, то есть истина, и чат молча исключался из выгрузки при обратном указании в файле.
- Перекачивание битых файлов (`verify`, `run --verify`) не оставляет загрузок без хозяина: отказ запроса очередной пачки и прерывание отменяют уже запущенные задачи, которые иначе продолжали писать в закрываемое состояние. Число одновременно созданных задач ограничено окном -- семафор ограничивал выполнение, но не количество задач и удерживаемых ими сообщений; ответ сопоставляется с запросом по идентификатору сообщения, а не по порядку.
- Прерванный `run --verify` не сообщает о ложных ошибках: файлы, до которых проход не дошёл, объявляются непроверенными, а не сломанными -- прежде каждый из них давал строку ошибки и попадал в счёт «N files still have issues».
- Прерванный по Ctrl+C прогон больше не называет себя завершённым: сводка печатается под заголовком `Export interrupted — state saved:`.
- Закрытый конвейер (`state show --json | head -20`, `list | less` с ранним выходом) завершает команду сигналом, как принято в оболочках, а не кодом `1` без единого слова: обёртка с `set -o pipefail` читала обычный ранний выход читателя как отказ экспорта.
- Профильные фото и истории скачиваются в том же окне `concurrent_downloads`, что и медиа чатов: фаза общих данных ждала каждый файл до перехода к следующему, и сотня историй превращалась в сотню обменов подряд.
- Релизный путь объявлен целиком: раннер закреплён (`ubuntu-24.04`), интерпретатор задан (`UV_PYTHON`), тег обязан быть аннотированным, а дата раздела сверяется с датой создания тега, а не коммита -- релизный коммит, полежавший в `master`, требовал в CHANGELOG свою дату вместо даты выпуска.
- Классификатор macOS убран из метаданных: ни один прогон его не подтверждает, а README и так говорит, что работа на macOS ожидается, но не проверяется.
- Границы покрытия по модулям снова следуют факту, а гейт сообщает об отставании сам: граница, ушедшая вниз больше чем на пять пунктов, ловит только обвал и пропускает регрессию, ради которой заведена.
- Сверка `scripts/check.sh` с CI считает команды построчно: проверка внутри многострочного шага `run:` (такие шаги в конвейере публикации уже есть) для сверки не существовала.
- Состав опций каждой команды закреплён проверкой по её разделу `docs/cli.md`: прежде сверялось только наличие самой команды, и новая опция описывалась лишь в `--help`.
- База состояния, которая не закрылась, меняет исход прогона. Отказ перехватывался внутри `close` и дальше журнала не шёл: несостоявшийся сброс WAL -- это записи прогона, оставшиеся ненаписанными, а пользователь читал «Export complete» и код 0.
- Нечитаемое число сообщений диалога записывается в журнал, а не превращается в ноль молча -- как это делает разбор типа чата по соседству.
- Вопрос, на который некому ответить, отвечается отказом, а не мнимым прерыванием. Пустой stdin (cron, systemd, CI, `< /dev/null`) давал «Interrupted.» и код `130`, который супервизор читает как «убит сигналом»; теперь команда завершается кодом `1` и называет флаг, которым вопрос обходится: `--yes` у `purge` и `state reset`, `--name`/`--api-id`/`--api-hash` у команд `auth`.
- Диагностика и журнал вне терминала пишутся строкой на запись. rich брал ширину 80 и переносил текст, добивая строки пробелами: при `tg-export run 2>> export.log` путь рвался посередине, `grep` по нему ничего не находил, а сборщик журналов получал по четыре записи вместо одной.
- `account default NAME --json` печатает `{"default": "NAME"}` вместо пустого stdout: это было единственное место, где флаг не давал документа, и `jq` падал разбором пустого входа.
- Взаимоисключающие аргументы отвергаются с кодом `2` и блоком usage, как соседний случай `--truncate`/`--no-truncate`: `list --format yaml --json` называл формат дважды и молча выдавал JSON, `tg info 123 --type personal` опрашивал все перечисленные чаты, будто отбора не просили.
- Релизный конвейер можно отрепетировать до постановки тега: `publish.yml` запускается вручную и проходит сборку целиком (сверка номера с манифестом и CHANGELOG, весь набор проверок, сборка, smoke-тест wheel, выгрузка артефактов), а публикацию на PyPI и создание release пропускает.
- Гейт отказывает на номере версии не вида `X.Y.Z`. Номер иной формы не попадал в список разделов, сверка размера бампа пропускалась целиком, и `1.6` при разделе с ломающими изменениями выпускался беспрепятственно; pre-release-номер вдобавок помечался на GitHub как последний выпуск.
- Проверка гонки в строке состояния воспроизводит смену чата ровно в окне гонки вместо перебора наудачу в течение двух секунд: вердикт зависел от планировщика, а на исправной сборке проверка всегда занимала полные две секунды и держала ядро занятым.
- Перенос уже имеющегося файла в каталог чата описан одним помощником. Три источника переиспользования -- другой чат того же аккаунта, соседний аккаунт, выгрузка Telegram Desktop -- повторяли один блок из пяти шагов дословно, и каждое изменение политики имён приходилось вносить трижды.

- Разделы общих данных (личные данные, контакты, сессии, профильные фото, истории, мелодии, прочее) объявлены одним перечнем.
- Сборка объекта из сохранённой записи (текстовая часть, реакция, кнопка) написана одним помощником вместо трёх разных приёмов, один из которых забирал поле `type` из переданного словаря.
- Документация приведена к тому, что делает код. Справочник обещал, что обратимый сброс вопросов не задаёт, тогда как `state reset --all` спрашивает независимо от `--delete-messages`; приватный маршрут сообщения об уязвимости назван в README и стал ссылкой в шаблоне отчёта об ошибке -- прежде `SECURITY.md` упоминался только в руководстве контрибьютора.
- Отказы, которые прогон гасил внутри себя, доходят до его исхода. `takeout clear` при недостижимом сервере (обрыв связи, таймаут) сохраняет идентификатор сессии и завершается кодом `1`: прежде единственная ссылка на висящую сессию стиралась безвозвратно, а команда рапортовала успех; отказ сервера по существу по-прежнему означает, что идентификатор можно стереть.
- Набор проверок и правила репозитория перестали зависеть от личных настроек владельца. `.gitignore` проекта закрывает `.claude/` и `docs/__explore/` сам -- прежде дерево оставалось чистым только благодаря глобальному ignore владельца, а у другого участника эти файлы попадали в `git add -A`.
- Файлы, которые пишут запросные команды, создаются доступными только владельцу. Каталог из `list --output-file` несёт id, имена и счётчики сообщений -- ровно то, ради чего шаблон конфига пишется приватным, -- а `tg info --output-file` ещё и тексты последних сообщений; обе точки писали файл по umask, то есть 0644, как и `<msg_id>.txt` у `tg download`.
- Ссылка вида `//host/path` или `\\host\share` из сообщения больше не попадает в страницу чата: проверка схемы принимала её за относительную.
- Запись, сделанная другой версией, больше не роняет страницу чата. Медиа или системное сообщение неизвестного класса разбиралось запасной веткой в базовый тип, которому тут же передавались поля производного, -- и она давала ровно тот отказ, который должна была предотвращать; ошибка приходила при рендере месяца, теряя не запись, а страницу.
- Итог по историям и мелодиям больше не складывает удачные записи с неудачными. Запись попадает в список независимо от того, скачалось ли медиа, поэтому десять историй с двумя отказами читались как двенадцать штук, а в журнал уходило «2 of 12».
- Отказ релизного гейта из-за размера версии называет настоящую причину. Сообщение строилось в предположении, что до него доходят только minor и major, поэтому при номере, который не является шагом вверх над секцией ниже (секция продублирована, порядок нарушен, номер понижен), оно называло раздел «Добавлено», которого в заметках нет, требовало «patch» и «1.3.0 или позже» в одной фразе, а настоящую причину не упоминало.
- Тяжёлые операции с диском при проверке целостности уведены с цикла событий. Уборка временных каталогов обходит всё дерево выгрузки рекурсивно, со `stat` на запись; выгрузка держит сотни тысяч файлов, и такой обход занимает секунды, в течение которых не обслуживались ни обмен с Telegram, ни Ctrl+C. Туда же переведено закрытие читателей соседних баз: оно берёт ту же блокировку, что запрос, а запрос ждёт занятого писателя до 30 секунд.
- Выход из конвейера загрузок доводит ожидание отменённых задач до конца, глуша приходящие в него отмены -- так же, как это делает защищённая запись в базу.
- Перекачивание битого файла идёт под той же политикой повторов, что и выгрузка: преходящий отказ (обрыв связи, таймаут, ответ сервера об ожидании) повторяется с экспоненциальной паузой, а отказ, который повтор не изменит (нет места, нет прав, файловая система только для чтения), не повторяется вовсе.
- Отказ фазы проверки больше не уносит итог прогона. Отказ базы или сети вокруг перекачивания выходил из `run` целиком: сводка не печаталась, индексная страница не создавалась, накопленный список ошибок терялся, и многочасовой экспорт, уже записанный на диск, выглядел как полностью упавшая команда.
- Исход перекачивания разбирается по перечислению, а не по признаку «не пусто»: исход, добавленный в перечисление и не разобранный в месте показа, засчитывался в перекачанные и отчитывался как починенный файл.
- Пример конфигурации в README загружается: у правила чата стоял ключ `action: skip`, которого загрузчик не знает -- он принимает `skip: true`, -- а неизвестный ключ отвергает файл целиком.
- Карта пакета в CONTRIBUTING называет `verify.py`: модуль появился, а таблица, объявленная в том же разделе актуальной картой, о нём умалчивала.
- Настройки `left_channels` и `archived` со значением `export_with_defaults` действительно выгружают такие чаты.
- Медиа-настройки папки не перекрываются правилом типа чата. Документация и сам метод подбора объявляют приоритет `chats > folders.chats > folders > type_rules`, но правило типа проверялось раньше правила папки: канал в папке с `media: all` скачивался по настройкам `type_rules.channels`.
- Булевы настройки общих данных (`personal_info`, `contacts`, `sessions`, `userpics`, `stories`, `profile_music`, `other_data`) проверяются на тип, как и остальные разделы конфигурации.
- `parse_size` отвергает значения, которые не могут быть размером: `max_file_size: true` превращался в один байт, то есть в запрет скачивать что-либо, а отрицательное число давало тот же запрет с другой стороны.
- Пароль прокси не попадает в `config --json`: секция уходила в машиночитаемый вывод сырой, тогда как в тексте той же команды пароль всегда был скрыт как `***`, а `api_hash` исключён намеренно.
- Перекачивание битого файла выбирает имя назначения через тот же реестр, что и выгрузка. Замена скачивается во временный каталог, где ничего нет, поэтому Telegram в каждой корутине отвечает базовым именем: два файла, которые экспорт развёл как `photo.jpg` и `photo (1).jpg`, переносились на один путь, второй перенос затирал первый, а уцелевшая запись в базе получала чужой размер.
- Запись о скачанном файле доходит до базы, даже если загрузку отменили в этот момент. Файл к тому времени уже лежит на месте, а конвейер загрузок штатно снимает задачи, оставшиеся в полёте: защита стояла только на коммите, поэтому отмена, пришедшая в сам INSERT, оставляла файл на диске без строки в `files` -- следующий прогон удалял его как осиротевший и скачивал заново.
- `tg download` сравнивает скачанное только с тем, что скачал сам. Набор для отсева дублей собирался из всего содержимого выходного каталога -- а он по умолчанию текущий, -- и включал только что записанный `<msg_id>.txt`: посторонний файл того же размера с теми же первыми 64 КБ приводил к удалению скачанного медиа без единой строки об этом.
- `account list` не показывает промежуточный файл входа как аккаунт. Вход пишет в `.<alias>.session.new.session` и подменяет рабочий файл только после успеха, а отбор шёл по суффиксу `.session`: процесс, убитый посреди входа, оставлял запись, которую перечисление показывало аккаунтом, а `auth check` пытался открыть.
- Снимок идущих загрузок стал копией значений, а не ссылок. Записи прогресса правились по полям из цикла событий, тогда как поток отрисовки читал их вне замка: в один кадр попадали объём принятого от нового вызова колбэка и общий размер, ещё равный нулю, -- rich получал `completed` без `total` и перерисовывал полосу назад.
- Один кадр живого статуса собирается по одному снимку текущего чата. Полоса прогресса и обе строки состояния брали снимок каждая, и при смене чата между ними в кадре оказывались полоса нового чата и счётчики предыдущего -- та самая рассогласованность, ради которой снимок и заведён.
- Повторная отмена во время ожидания защищённой записи больше не срывает это ожидание. Удержание вызывающего до конца commit держалось на незащищённом `await`: второе нажатие Ctrl+C приходило прямо в него, вызывающий уходил закрывать соединение, и commit падал с `ValueError: Connection closed` в задаче, которую никто не ждёт.
- Прогресс чата в `export_state` больше не откатывается записью из копии, снятой в начале обхода. Защита от отката стояла только на `last_msg_id`, а отметка спуска вниз по истории (`oldest_msg_id`) и признак дочитанного чата (`full_history`) писались присваиванием: второй процесс, которого не остановила advisory-блокировка -- её нет там, где нет `fcntl`, и она не действует между машинами на сетевом хранилище, -- поднимал отметку наверх и снимал признак, после чего пропуск в истории оставался навсегда, потому что фаза 2 для такого чата больше не запускалась.
- Загрузка не повторяется на отказах, которые повтор не меняет. `OSError` целиком считался преходящей ошибкой, поэтому «нет места», «нет прав», «файловая система только для чтения», «слишком длинное имя» и превышение квоты проходили три попытки с ожиданием 2**attempt секунд каждая: исчерпание места превращалось в долгий холостой проход по всему каталогу.
- Отмена во время открытия базы состояния освобождает блокировку и закрывает соединение. Перехватывался `Exception`, а второй Ctrl+C приходит как `CancelledError` (наследник `BaseException`): отмена между захватом блокировки и концом открытия оставляла блокировку взятой, а соединение -- открытым, причём `__aenter__` не завершался, поэтому закрыть его было уже некому и поток aiosqlite жил до конца процесса.
- Отказы на путях освобождения ресурсов и переиспользования файлов записываются в журнал. Прежде молча гасились: отказ закрытия базы (например, при сбросе WAL) -- пользователь читал «Export complete» и код 0; отказ освобождения takeout-контекста, у которого есть последствие на сервере; неудачная ссылка или копия уже скачанного файла, из-за чего вместо переиспользования шла полная загрузка; нечитаемый заголовок выгрузки Telegram Desktop, из-за которого чат просто не попадал в индекс импорта.
- Конфигурация аккаунта попала под ту же защиту прав, что и остальные файлы каталога настроек. `init` дописывает в неё по строке на каждый чат -- идентификатор, имя и число сообщений, то есть полный список контактов, групп и каналов, -- а файл создавался с правами по umask, и при чтении его режим не проверялся, в отличие от `config.yaml` с паролем прокси.
- Нижняя граница `setuptools` в `[build-system]` поднята с 68.0 до 83.0.0. Прежняя граница допускала версии с тремя записями в OSV: внедрение команды через URL пакета и запись файлов за пределы каталога (обе HIGH), а также обход исключений `MANIFEST.in` при сборке sdist -- последнее относится напрямую к этому проекту, поскольку дистрибутив собирается из рабочего дерева, где рядом лежат выгрузка и файлы покрытия.
- Путь к базе состояния кодируется при подстановке в SQLite-URI и в потоковом рендере, а не только при обращении к соседней базе.
- Файлы с секретами создаются приватными, а не ужимаются вторым шагом. `api_credentials.yaml`, файл сессии с ключом авторизации и база состояния создавались с правами по umask (обычно доступными на чтение всем), и `chmod 0600` шёл следом: в этом окне другой локальный пользователь успевал открыть дескриптор, который сохраняет доступ и после смены прав.
- Папки, заданные флагами фильтра (`contacts`, `groups`, `broadcasts`, `bots`), применяются и к архивным чатам.
- `purge` сообщает отказ базы, а не выдаёт его за отсутствующий чат. Разбор числового идентификатора и запрос к каталогу делили один `except ValueError`, а `ValueError` возбуждает и aiosqlite при закрытом соединении: такая ошибка уводила выполнение в поиск по имени с аргументом-числом и заканчивалась сообщением «No chats found matching '<id>'».
- `state reset --delete-messages` обнуляет и записанное число сообщений. Сообщения удалялись, а колонка `messages_count` сохраняла прежнее значение, и строка чата оставалась внутренне противоречивой: индексная страница берёт записанное число в обход фактического `COUNT(*)`, поэтому чат с пустой таблицей продолжал объявлять прежние тысячи сообщений.
- Чат, о котором известно, что выгруженных сообщений в нём нет, показывается нулём. Сводка по чатам пропускала нулевые значения, вызывающий не находил чат в словаре и подставлял `chat.messages_count` -- идентификатор последнего сообщения, который Telegram отдаёт вместо счётчика, поэтому пустой чат объявлялся на индексной странице числом в тысячах.
- Признак «история выгружена целиком» больше не выставляется проходом, остановленным границей `date_from`.
- История, скачанная файлом без расширения, отрисовывается как фотография. Расширение проверялось вхождением суффикса в строку (`suffix in ext`), а пустая строка входит в любую: файл без расширения попадал в `<video>` вместо `<img>` и не показывался.
- Справка `--account` называет команду, которая существует. Одиннадцать объявлений опции описывали её двумя разными способами, и шесть из них отсылали к `auth default`: такой команды нет, аккаунт по умолчанию задаёт `account default`, и пользователь, следующий подсказке, получал `Error: No such command 'auth default'`.
- `tg info` без идентификаторов и без `--from-catalog` завершается кодом 2 с блоком usage, а не нулём: ветка печатала подсказку и возвращала пустое значение, которое вызывающий читал как успех -- под `--quiet` команда молчала и всё равно сообщала об успешной работе.
- Параллельность загрузок держится и в чате с редкими вложениями. Окно конвейера считалось по числу сообщений в очереди, а не по идущим загрузкам: текстовое сообщение заводило задачу и занимало место в окне, поэтому при вложениях реже, чем одно на `concurrent_downloads` сообщений, цикл стоял на ожидании самой старой задачи, а за ней в очереди ждали уже завершённые тексты -- и одновременно шла ровно одна загрузка.
- Отмена прогона больше не превращается в отказ одного чата. `CancelledError` гасилась при выгрузке чата и возвращалась как «этот чат не удался»: цикл выходил, флаг принудительной остановки оставался снятым, и сразу после просьбы остановиться запускалась фаза глобальных данных -- контакты, сессии, истории, аватары.
- Два разных файла с одинаковым именем исходника больше не пишутся по одному пути. Загрузки сериализовались по `file_id`, а бороться им приходится за имя в каталоге назначения: Telegram массово отдаёт `photo.jpg` и `document.pdf`, поэтому две корутины видели место свободным одновременно, первая делала ссылку, вторая копировала поверх неё, и прогон заканчивался одним файлом на диске и двумя записями в состоянии, указывающими на него; проверка размера при этом удаляла файл, который сосед только что положил.
- Занятый другим процессом файл сессии сообщается, а не молча пропускается. Отказ «database is locked» при чтении состояния Takeout обрабатывался вместе с «такую форму таблицы читать нечем»: значение оставалось в колонках, а запуск шёл дальше -- в ту самую позиционную распаковку Telethon, из-за которой сохранённый `takeout_id` попадает в слот ключа и старт падает с `TypeError`.
- `tg-export init` не перезаписывает существующую конфигурацию: команда завершается кодом 1 и называет путь, а перезапись запрашивается флагом `--force`, который сохраняет прежний файл рядом как `<имя>.bak`.
- Опечатка в имени ключа внутри секции конфигурации сообщается, а не подменяется умолчанием. Прежде состав ключей сверялся только на верхнем уровне: `max_size` вместо `max_file_size` оставлял предел 100 МБ вместо заданных 10, `date_form` вместо `date_from` выгружал всю историю вместо среза, а `unmatched: export_with_defaults`, написанный скаляром, сводился к `skip` -- к действию, противоположному написанному.
- Учёт скачанного файла падал с `TypeError` на Python 3.11: исход загрузки проверялся на членство в перечислении, а такая проверка значения возвращает `bool` только начиная с 3.12.
- Экспорт останавливается, когда на диске кончилось место. Ошибка нехватки места перехватывалась наравне с отказом отдельного файла, поэтому ветка остановки не срабатывала: прогон шёл по всем оставшимся сообщениям, ничего не скачивая, и складывал в сводку по строке на каждое медиасообщение.
- Отказы фазы глобальных данных (личные данные, контакты, сессии, аватары, истории, рингтоны) попадают в сводку и в код возврата.
- Прерывание по Ctrl+C вне цикла экспорта завершает процесс кодом 130, а не 1 с сообщением «Aborted!».
- `run --verify` не удаляет повреждённый файл до того, как скачана замена. Команда `verify` была исправлена для этого раньше, но перекачивание было реализовано дважды, и правку получила только одна копия; теперь реализация одна.
- Чат, рендер которого был прерван, достраивается на следующем прогоне. Признаком готовности считался любой файл по маске `messages*.html`, под которую подпадают уже записанные помесячные страницы, поэтому месяцы после точки прерывания не появлялись, а ссылка с индексной страницы вела на несозданный `messages.html`.
- Строка состояния и главная полоса прогресса читают счётчики текущего чата одним согласованным снимком.
- Скорость в строке состояния считается по текущему чату, а не по всему прогону: числитель (байты и сообщения) сбрасывался на каждом чате, а знаменатель продолжал расти с начала запуска, и через час экспорта показанная скорость была занижена в десятки раз.
- Вторая фаза экспорта продолжается с того места, где остановилась первая. Прерывание между фазами оставляет нулевой `oldest_msg_id` при непустом `last_msg_id`, и обход шёл с самого свежего сообщения, то есть чат перебирался целиком заново.
- Проверка файлов сообщает о своих отказах, а не о всех накопленных за прогон: в итог `verify` попадала длина общего списка ошибок, включая ошибки скачивания предыдущих чатов.
- Пути переиспользования файлов (соседний чат того же аккаунта, выгрузка соседнего аккаунта, импорт из tdesktop) сверяют размер уже существующего файла, а не только совпадение имени.
- Покинутые каналы читаются постранично. `GetLeftChannelsRequest` вызывался ровно один раз с `offset=0`, и при числе покинутых каналов больше страницы остальные не попадали в каталог и не обрабатывались правилом `left_channels_action` -- без признаков в журнале.
- Команда `state reset` отличает не переданный идентификатор чата от нулевого: проверка `not chat_id` трактовала `0` как «не задан».
- Возможности, описанные в документации, но не работавшие в коде, приведены в соответствие. `tg-export init --from <каталог>` действительно записывает конфигурацию: прежде команда читала YAML, отбрасывала результат разбора и печатала «Config saved», не создав файла, а следующая команда сообщала «Config not found».
- Ошибки экспорта стали наблюдаемыми. Сбой отдельного файла теперь пишется в лог с идентификаторами чата и сообщения и с трассировкой, а не только увеличивает счётчик: прежде «Errors: 137» не поддавалось расследованию ни при каком уровне логирования, потому что исключение не доходило до logging.
- Непредвиденная ошибка (Telethon, sqlite, сеть) выводится строкой `Error: <тип>: <текст>` с подсказкой про `--debug`, а не полной трассировкой поверх незакрытого прогресс-бара.
- Ветка двухфакторного входа выбирается по типу исключения Telethon (`SessionPasswordNeededError`, `PasswordHashInvalidError`), а не по подстроке в имени класса.
- Неудачный вход больше не оставляет аккаунт без сессии. `auth add` теперь логинится в отдельный файл и занимает штатный путь сессии только после успешного `get_me()`; прежде рабочий файл удалялся до входа, и неверный код, обрыв связи или Ctrl+C на приглашении лишали пользователя и старой сессии, и новой -- восстановить её можно было только повторным полным входом с кодом из Telegram.
- База состояния, созданная прежней версией, приводится к текущей схеме при открытии. Схема создавалась только через `CREATE TABLE IF NOT EXISTS`, а на существующем файле это ничего не меняет: колонка `is_archived`, добавленная в `catalog_cache`, не появлялась, и первая же запись каталога падала с `OperationalError: table catalog_cache has no column named is_archived` -- уже внутри запущенного экспорта.
- Форматирование сообщений с эмодзи больше не теряется и не смещается. Telegram задаёт границы entity (жирный, курсив, ссылки, код) в кодовых единицах UTF-16, а разбор резал Python-строку по кодовым точкам: после первого же символа вне BMP -- любого цветного эмодзи, части иероглифов, музыкальных знаков -- все последующие границы сдвигались, и entity либо не проходила проверку границ и молча отбрасывалась вместе с разметкой, либо вырезала соседний фрагмент, из-за чего подпись ссылки переставала соответствовать её адресу.
- `verify` больше не берётся за файлы, пропущенные намеренно. Отбор шёл по условию `status != 'done'`, которое смешивало «не докачано» и «пропущено по размеру или по типу»: команда пыталась перекачать ровно те файлы, которые конфигурация исключила.
- Служебные отметки времени в базе состояния (`updated_at`, `downloaded_at`) пишутся в UTC с явным смещением, как и даты сообщений: прежде одинаково объявленные колонки хранили значения двух форматов -- наивное локальное время и момент со смещением, -- что делало их несравнимыми при переносе базы между часовыми поясами.
- Ожидание блокировки базы задано явно (30 секунд) и одинаково для всех соединений: рабочего, read-only-чтения помесячных страниц и поиска файлов в базе соседнего аккаунта.
- Из настроек соединения убран `PRAGMA foreign_keys = ON`: внешних ключей в схеме нет, и прагма обозначала защиту, которой не существует.
- Страницы чата не перерисовываются, когда чат не изменился. Прежде рендер шёл безусловно: все ранее собранные страницы удалялись и строились заново -- с загрузкой каждого месяца из SQLite и разбором JSON-полей каждого сообщения, -- даже если инкрементальный запуск не принёс ни сообщения, ни файла.
- Индексная страница читает число сообщений одним запросом на все чаты вместо одного-двух запросов на каждый чат: у аккаунта с сотнями чатов это были сотни обращений к базе на построение одной страницы.
- Служебные запросы к таблице файлов перечисляют нужные колонки вместо `SELECT *`; они выполняются на каждый медиафайл, то есть в самом горячем пути экспорта.
- Границы версий зависимостей приведены к проверенным: `jinja2>=3.1.6` (первый выпуск без пяти уязвимостей, затрагивающих 3.1.0-3.1.5), `click>=8.3.3` (исправлено внедрение команды в `click.edit()`, которую проект не вызывает), `telethon>=1.36,<2` (в Telethon v2 слой сессий переписан, и класса `SQLiteSession`, вокруг которого построен обход ошибки порядка колонок, там нет), `python-socks[asyncio]>=2.0,<3` (Telethon правит приватные внутренности этой библиотеки, а сочетание с вышедшей 3.0.0 не проверялось).
- Конфигурация проверяется при загрузке, а не отказывает молча в середине экспорта. `concurrent_downloads` сверяется с документированным диапазоном 1-5: значение `0` уходило прямо в `asyncio.Semaphore` и подвешивало загрузку медиа без сообщения и без таймаута, строка в кавычках и отрицательное число давали `TypeError`/`ValueError` с трассировкой.
- Глобальный `config.yaml` проверяется наравне с остальными файлами. Опечатка в имени секции (`proxi:` вместо `proxy:`) или прокси, записанный строкой вместо словаря, приводили к подключению напрямую без единого сообщения -- то есть ровно к тому исходу, ради предотвращения которого запуск прерывается при отсутствии `python-socks`.
- Синтаксическая ошибка YAML в конфиге аккаунта выводится строкой `Cannot parse <файл>: ...` вместо трассировки.
- `min_free_space: 0` действительно отключает проверку свободного места: значение по умолчанию подставлялось через `or`, поэтому ноль заменялся на 20 ГБ. Само значение по умолчанию объявлено один раз и больше не расходится с тем, что показывает `tg-export config`.
- `~` раскрывается в `output.path` и в `--output`. Прежде запись `path: ~/exports` создавала каталог с именем `~` в текущем рабочем каталоге, и весь экспорт уходил туда.
- Файлы конфигурации читаются в UTF-8, а не в кодировке локали. Имена папок и чатов на кириллице на системе с не-UTF-8 локалью приводили либо к отказу чтения, либо к искажению имён, из-за которого правила молча переставали срабатывать.
- Команда `verify` больше не удаляет битый файл до того, как получит замену. Файл скачивается во временный каталог рядом с целевым и переносится атомарным переименованием только после успеха; обрыв связи или Ctrl+C оставляет прежний файл на месте.
- Потеря `takeout_id` на файлах сессии с физическим порядком колонок `(..., auth_key, tmp_auth_key, takeout_id)`.
- Падение старта на файле сессии схемы `version = 7` с активным Takeout (`TypeError: object supporting the buffer API required`): такая схема больше не пропускается обходом.
- Jinja-шаблоны и статика (CSS, JS, иконки) теперь попадают в дистрибутив. Без `[tool.setuptools.package-data]` в колесо уходили только `*.py`, поэтому любой экспорт после `pip install tg-export` падал с `TemplateNotFound: 'index.html.j2'`; дефект действовал с версии 1.0.0.
- Прерывание фазы 1 (Ctrl+C) больше не оставляет безвозвратно пропущенный интервал сообщений. Фаза 1 идёт от новых сообщений к старым, поэтому указатель `last_msg_id` продвигается только после её полного прохода; фаза 2 спускается от `oldest_msg_id` и в пропущенный интервал не заходила, так что потерянные сообщения не забирал никто.
- Указатель `last_msg_id` больше не откатывается назад: запись из копии, прочитанной в начале экспорта чата, не может уменьшить уже достигнутое значение.
- Удалена вторая, неиспользуемая реализация разметки сообщения. Блок сообщения собирался и шаблонами Jinja, и конкатенацией строк на Python, причём реализации уже разошлись: в шаблонной у отметки времени есть всплывающая подсказка с полной датой, в ручной её не было, а порядок кнопок и реакций был обратным.
- URL inline-кнопки в HTML-выгрузке проходит проверку схемы: `javascript:` в кнопке попадал в готовую страницу и выполнялся при нажатии.
- Файлы с секретами и личными данными создаются доступными только владельцу: файл сессии Telegram с ключом авторизации (был `0644`), база состояния с текстами всех сообщений, телефонами и адресами сессий, каталог выгрузки.
- Ввод `api_hash` при `auth credentials` скрывается: набранный в открытую, он остаётся в истории оболочки.
- Имя аккаунта проверяется перед подстановкой в путь файла сессии и конфигурации: разделитель пути или ссылка на родительский каталог в имени размещали и удаляли файлы за пределами каталога настроек.
- Путь к базе соседнего аккаунта экранируется при сборке SQLite-URI: символ `?` в пути превращал остаток в параметры и снимал режим «только чтение».
- Файл блокировки состояния больше не удаляется при освобождении. `flock` привязан к inode, а не к имени: удаление позволяло процессу, успевшему открыть файл, удерживать блокировку на осиротевшем inode, пока следующий создавал новый файл и брал блокировку на нём.
- Файл сессии Telegram защищён собственной блокировкой. Прежняя блокировка привязана к каталогу вывода, поэтому не мешала ни `tg send` рядом с идущим экспортом, ни второму экспорту с другим `--output`: обе команды работали с одной сессией, а Telethon отвечает на это порчей ключа авторизации в файле.
- Принудительное завершение (второй Ctrl+C подряд) снимает только задачу экспорта. Раньше отменялись все задачи цикла событий, включая внутреннюю задачу `asyncio.shield`, то есть ровно ту защиту, ради которой shield и поставлен: запись пачки сообщений и удаление данных чата могли остаться применёнными наполовину.
- Защищённая запись удерживает вызывающего до своего конца. `asyncio.shield` защищает операцию, но не вызывающего: тот получал отмену немедленно, доходил до закрытия соединения, и идущий commit падал в неотловленной задаче с `ValueError: Connection closed`.
- Команда `run` освобождает файл блокировки состояния и соединение, если отказ случился между их захватом: раньше оба захватывались до блока, который их освобождает.
- Установка обработчиков сигналов не роняет экспорт на платформах, где она не поддерживается (Windows): там Ctrl+C приходит обычным прерыванием, которому команда и так сопоставляет код `130`.
- Блокирующие операции вынесены из потока цикла событий. Поиск файла в базе соседнего аккаунта открывал SQLite обычным `sqlite3` и мог ждать занятого писателя до 30 секунд; копирование файла из выгрузки tdesktop и запасная ветка связывания между чатами читали и писали файл целиком; страницы глобальных данных и индекс собирались шаблонизатором при живом соединении с Telegram.
- Загрузки медиа внутри чата идут параллельно, как обещают настройка `concurrent_downloads` и документация.
- Уборка после неудачной загрузки удаляет только собственные недокачанные файлы. Раньше удалялось всё, что появилось в общем каталоге чата с момента снимка, снятого ещё до постановки в очередь загрузки, так что при одновременных загрузках сносились файлы, только что дописанные соседней.
- Прогресс отправки (`tg send`) не рисуется, когда вывод не является терминалом: раньше проверялся только `--quiet`, и при перенаправлении в файл или конвейер туда попадали перерисовки бара.
- Прогресс альбома больше не уходит за 100%. Telethon режет альбом на группы по десять и передаёт в обратный вызов остаток списка (25, затем 15, затем 5), тогда как счётчик отправленного считается от начала альбома; это значение перетирало общее число файлов.
- Вид полосы прогресса одинаков в обоих режимах отправки: проценты показываются и при побайтовом счёте, и при альбомном, а размер и скорость добавляются к ним, когда счёт идёт по байтам.
- Имя файла в прогрессе отправки (`tg send`) экранируется перед выводом. rich разбирает описание задачи как разметку, поэтому имя вида `[draft]report.txt` печаталось как `report.txt`: квадратные скобки съедались вместе с содержимым.
- Флаг `--quiet` больше не глушит причину отказа. Признак «существенное сообщение» проставлялся вручную у отдельных вызовов, и из 94 мест его имели 20, причём 17 из них -- строки итоговой сводки; в результате `--quiet tg send 123` печатал пустой вывод и возвращал `1`, а одно и то же сообщение `Config not found` было видно в `run` и терялось в `state show`, `state reset` и `verify`.
- Ограничение размера файла для Takeout-сессии считается по всем применимым правилам, а не только по `defaults.media`.
- Диагностика состояния файла сессии различает три разных состояния вместо одной строки на все. Сообщение «Detected stale takeout_id/tmp_auth_key ... staging restore» печаталось при каждом запуске, включая полностью исправный: Telethon при `store_tmp_auth_key_on_disk = false` всегда пишет в `tmp_auth_key` пустое значение, поэтому признак «в строке что-то есть» был истинным всегда, а восстанавливать при этом было нечего.
- Интерактивный логин (`account add`) открывает файл сессии через `FixedSQLiteSession`, а не по строковому пути.
- Отказ Takeout больше не поглощается широким `except Exception` -- обрабатываются только ошибки, которые действительно означают недоступность Takeout, а дефекты кода доходят до вызывающего.

## [1.2.6] -- 2026-05-18

### Исправлено

- `_extract_and_clear` в `FixedSQLiteSession`: type-валидация `takeout_id` и `tmp_auth_key`, `has_data` через `is not None` (раньше `bool(b'')==False` пропускал пустые BLOB как «нет данных»). Telethon при `store_tmp_auth_key_on_disk=False` пишет `b''` в physical позицию `tmp_auth_key`, а swap-баг при следующем чтении ставит `session._takeout_id = b''`, что валит сериализатор `InvokeWithTakeoutRequest(takeout_id=b'')` с `struct.error: required argument is not an integer`. Дополнительно post-init валидация: если после `super().__init__()` `_takeout_id` оказался non-int -- clear.
- Атомарный `commit_phase_progress` в `ExportState` ([tg_export/state.py](tg_export/state.py)). Ранее фаза 2 делала 4 раздельных commit-а (last/oldest/full_history/messages_count); прерывание сети между ними оставляло несогласованное состояние, и `set_oldest_msg_id` мог упасть с `NOT NULL constraint failed: export_state.last_msg_id`. Все четыре сеттера переведены на единый `_upsert_chat_state` с whitelist колонок и явным `last_msg_id=0` в INSERT-ветке. Схема: `last_msg_id INTEGER NOT NULL DEFAULT 0`.
- Кооперативное прерывание HTML-рендера в `render_chat_streaming` и `_render_index` через параметр `should_stop`. Force shutdown зависал после «state saved», потому что `asyncio.to_thread` ставит задачу в default `ThreadPoolExecutor`, `task.cancel()` прерывает только `await`, а сам thread продолжает Jinja2-рендер; `asyncio.run().__exit__` ждёт thread join() с таймаутом. Гранулярность прерывания -- month bucket; внутри одного `jinja2.render()` прерывания нет (CPython не позволяет прервать thread без yield).
- `chat_error_line` принимает опциональный `chat_id`, и сообщение об ошибке экспорта чата включает id (`Error exporting Alice (id=12345): ...`) для возможности ручной правки записи в `export_state`.

### Качество кода

- `cast(Any, ...)` для возвращаемых значений Telethon `get_personal_info()` / `get_top_peers()`: Pyright не разрешал доступ к `.full_user` / `.users` / `.categories` для `Union` без stubs.

## [1.2.5] -- 2026-05-08

### Исправлено

- Замена workaround'а 1.2.4 на корректный фикс через subclass `FixedSQLiteSession` ([tg_export/session.py](tg_export/session.py)). Перед `super().__init__()` читаем `takeout_id`/`tmp_auth_key` явно по именам колонок, обнуляем их на диске (чтобы баггованный позиционный unpack в Telethon не крашился на `AuthKey(data=int)`), затем восстанавливаем значения через сеттеры -- write-путь у Telethon корректный. Главное преимущество: `takeout_id` теперь **сохраняется между запусками**, прежний sanitize терял его и заставлял каждый запуск создавать свежий takeout (cooldown TAKEOUT_INIT_DELAY и повторное подтверждение в клиенте Telegram). Регрессионный тест в `tests/test_api.py` явно проверяет, что ванильный `SQLiteSession` крашится на той же фикстуре, на которой наш subclass работает корректно.

## [1.2.4] -- 2026-05-07

### Исправлено

- Workaround для асимметричного бага Telethon `SQLiteSession` 1.43+ ([commit 5a3a94eb](https://github.com/LonamiWebs/Telethon/commit/5a3a94eb)): `_update_session_table` пишет в порядке `(..., auth_key, takeout_id, tmp_auth_key)`, а `__init__` читает `select *` и распаковывает как `(..., key, tmp_key, takeout_id)` -- 5-й и 6-й столбцы переставлены местами. Пока обе колонки `NULL`, `AuthKey(data=None)` срабатывает по early-return и баг не виден; как только Takeout-экспорт сохраняет `takeout_id`, при следующем старте этот int попадает в `tmp_key`, и Telethon крашится с `TypeError: object supporting the buffer API required` из `sha1(int)`. Перестановка колонок не помогает -- read/write симметрично сломаны. `TgApi.__init__` теперь обнуляет `tmp_auth_key` и `takeout_id` через `_sanitize_session_file` перед открытием `TelegramClient`. `auth_key` (256 байт) сохраняется, перелогин не нужен; наш `start_takeout` всё равно начинает свежий takeout. Правильный фикс через monkey-patch `SQLiteSession` записан в [TODO.md](TODO.md).

## [1.2.0] -- 2026-05-07

### Безопасность

- Включено `autoescape` в Jinja2-шаблонах HTML-рендера: имена чатов, авторов, контактов, sessions и stories больше не позволяют XSS через `<script>` или `<img onerror>`.
- Добавлен whitelist URL-схем (`http`, `https`, `mailto`, `tel`, `tg`) и `rel="noopener noreferrer"` для всех `target="_blank"`-ссылок: `javascript:`/`data:`-инъекции через Telegram URL-entities и inline-кнопки больше не приводят к исполнению JS.
- `sanitize_name` отбрасывает `..`, управляющие символы, RTL-override; нормализует Unicode (NFKC); ограничивает длину 200 байт.
- `purge` больше не использует `rglob` -- сканирует только известные префиксы `unfiled/`, `archived/`, `left/`, `folders/*` и проверяет, что путь действительно внутри `output_base.resolve()`. Симлинки пропускаются.
- `tdesktop` import: пути из внешнего HTML валидируются через `is_relative_to(chat_dir.resolve())`.
- Sibling-БД: путь к файлу проверяется на принадлежность tree соседа; размер сравнивается с заявленным Telegram.
- Конфигурация: `~/.config/tg-export` принудительно получает 0o700; `api_credentials.yaml` валидируется на типы и слабые права.

### Исправлено

- Логика `last_msg_id` в фазе 2: накапливаем максимум через `phase2_max_id`, а не теряем после первого сообщения.
- `register_file` теперь явно делает `commit`: при kill -9 файл не остаётся незарегистрированным в БД.
- `_verify_files` использует тот же путь `register_file -> commit`, поэтому verify-результаты сохраняются и не теряются при `close()`.
- `_handle_shutdown` через `asyncio.shield` защищает идущий `commit` от отмены: повторный SIGINT не теряет batch до 500 сообщений.
- `_cleanup_orphaned_files` сравнивает абсолютные resolved-пути; запуск из другой cwd больше не приводит к удалению легитимных файлов как orphaned.
- `_download_if_new` сравнивает SHA-256 первых 64KB, а не только размер: два разных файла одной длины больше не схлопываются в один.
- `start_takeout` отлавливает `TakeoutInvalidError`/`TakeoutRequiredError` напрямую, а не через подстроку в `str(e)`.
- `cache_catalog` явно коммитит запись о чате: статистика не теряется, если экспорт прервался до первого batch-commit.
- Сообщение об отсутствии default-аккаунта указывает правильную команду `tg-export account default`, а не несуществующую `auth default`.
