## Устройство пакета

Поток одного экспорта: `cli` → `config` → `api` → `exporter` → `state` / `media` → `renderer`.
Команда разбирает аргументы и читает конфиг, поднимает соединение и базу состояния,
собирает `Exporter`, тот обходит чаты, складывает сообщения в SQLite и файлы на диск,
после чего рендерит HTML.

| №  | Модуль                    | Назначение                                                              |
|----|---------------------------|-------------------------------------------------------------------------|
| 1  | `cli/`                    | пакет команд: модуль на группу, `__init__.py` собирает их в `main`        |
| 2  | `config.py`               | чтение YAML-конфига и разрешение правил для конкретного чата              |
| 3  | `auth.py`                 | аккаунты: учётные данные, пути к файлам сессии и конфига                  |
| 4  | `api.py`                  | обёртка Telethon, режим Takeout, блокировка файла сессии                  |
| 5  | `session.py`              | подкласс `SQLiteSession`, обходящий порядок колонок в файле сессии        |
| 6  | `catalog.py`              | список чатов и генерация шаблона конфига по нему                          |
| 7  | `exporter.py`             | цикл экспорта: отбор чатов, две фазы выборки, живой статус                |
| 8  | `converter.py`            | перевод объектов Telethon в модели пакета                                 |
| 9  | `models.py`               | модели сообщения, медиа, служебных действий                               |
| 10 | `state.py`                | SQLite-состояние: сообщения, файлы, прогресс по чатам                     |
| 11 | `media.py`                | скачивание медиа, отбор по типу и размеру, повторное использование файлов |
| 12 | `importer.py`             | поиск уже скачанных файлов в экспорте Telegram Desktop                    |
| 13 | `html/renderer.py`        | рендер страниц через Jinja2                                               |
| 14 | `locking.py`              | advisory-блокировки: один процесс на файл сессии и на базу состояния      |
| 15 | `privacy.py`              | права доступа к файлам с секретами и личными данными                      |
| 16 | `format.py`               | форматирование размеров и скоростей                                       |
| 17 | `errors.py`               | доменные ошибки и коды возврата, которым они соответствуют                |
| 18 | `console.py`              | единственный `Console` вывода в stderr                                    |

Границы импортов: стандартная библиотека импортируется в шапке модуля — она уже загружена
интерпретатором, и выигрыша от отложенного импорта нет. Внутри тел функций остаются только
тяжёлые зависимости и модули самого пакета (`telethon`, `jinja2`, `tg_export.exporter`,
`tg_export.state`): их загрузка на каждый `--help` стоит около секунды. Правило закреплено
тестом `test_standard_library_is_imported_at_module_level`.

Границы слоёв: схему базы знает только `state.py` — команды обращаются к ней методами,
а не собственным SQL. Разметку страниц задают шаблоны `html/templates/`, а не строки в
Python. Сетевые вызовы идут через `api.py`, чтобы режим Takeout и блокировка сессии
действовали для всех команд одинаково.

Design-документы, с которых начинался проект (`docs/superpowers/`), в репозиторий не входят
и остаются локальными записями замысла: они описывают состояние на момент проектирования и
с кодом не сверяются. Актуальная карта пакета — таблица выше, принятые решения — `docs/adr/`.

## Окружение

Минимальная версия — Python 3.11 (`requires-python = ">=3.11"`). CI прогоняет тесты на
3.11, 3.12, 3.13 и 3.14; линтер, проверка типов и границы покрытия считаются на каждой
версии матрицы, а на 3.12 дополнительно выгружается отчёт покрытия в Codecov.
Платформа проверки — Linux (`ubuntu-latest`). На macOS работа ожидается, но не
проверяется; на Windows не проверяется тем более: там нет `fcntl`, и блокировка файла
сессии вырождается в отсутствующую, а обработчики сигналов не регистрируются
(`loop.add_signal_handler` поднимает `NotImplementedError`, экспорт продолжается без них).

Используется `uv` для управления зависимостями и виртуальным окружением.

```bash
# Установка uv: https://github.com/astral-sh/uv
uv sync
```

Инструменты разработки объявлены группой `dev` (PEP 735) и входят в набор `uv sync`
по умолчанию. Extra `proxy` -- напротив, необязательная зависимость самого пакета:
она нужна только при работе через прокси и ставится явно, `uv sync --extra proxy`.

Все команды разработки запускаются через `uv run`, без активации venv напрямую:

```bash
uv run tg-export --help
uv run python -m pytest
```

## Запуск тестов

```bash
uv run python -m pytest
```

Для подробного вывода:

```bash
uv run python -m pytest -v
```

Частичный прогон -- один файл или отбор по `-k` -- запускается с `--no-cov`:

```bash
uv run python -m pytest tests/test_models.py --no-cov
```

Причина: `--cov` включён в `addopts`, а порог покрытия применяется к результату
запуска целиком. Для одного файла покрытие заведомо ниже порога, и прогон
завершается кодом 1 при всех зелёных тестах; порог осмыслен только для полного набора.

Тесты не обращаются к Telegram API и не требуют сети.

Покрытие считается на каждом запуске (`--cov` задан в `addopts`), поэтому общий
порог из `[tool.coverage.report] fail_under` срабатывает и локально, а не только
в CI. Нижние границы по модулям проверяются отдельно -- их общий порог не ловит,
потому что хорошо покрытые мелкие файлы вытягивают среднее за крупные:

```bash
uv run python scripts/coverage_gate.py
```

Границы объявлены в `pyproject.toml`, секция `[tool.tg-export.coverage-floor]`,
и стоят чуть ниже фактических значений: они ловят падение покрытия, а не
требуют его роста. При осознанном снижении границу правят вместе с кодом.

## Проверки перед PR

Весь набор проверок, который выполняет CI, прогоняется одной командой:

```bash
scripts/check.sh
```

Порядок шагов тот же, что в `.github/workflows/ci.yml`: `uv lock --check`, `ruff check`,
`ruff format --check`, `pyright`, тесты с покрытием, границы покрытия по модулям.
Скрипт останавливается на первой упавшей проверке и возвращает её код.

Исправимое исправляется тем же скриптом -- он сначала прогоняет `ruff check --fix` и
`ruff format`, затем обычные проверки:

```bash
scripts/check.sh --fix
```

Расхождение скрипта с CI ловится тестом
`tests/test_code_style.py::test_one_command_runs_everything_ci_runs`: шаг, добавленный в
workflow и не добавленный в скрипт, роняет проверки.

Отдельные шаги, когда нужен только один из них:

```bash
uv run ruff check .
uv run ruff format --check .
uv run pyright
```

## Схема базы состояния

Схема объявлена одной строкой-константой `SCHEMA_SQL` в `tg_export/state.py`. Колонка,
добавленная в это объявление, применяется и к базам, созданным прежними версиями:
при открытии фактический состав таблиц сверяется с объявленным, недостающие колонки
добавляются `ALTER TABLE`. Поэтому новая колонка обязана иметь значение по умолчанию
или допускать `NULL` -- иначе добавить её к существующей таблице нельзя.

Изменение, которое добавлением колонки не решается (удаление колонки, смена типа,
перестроенный индекс), требует отдельного шага миграции и увеличения `SCHEMA_VERSION`:
версия хранится в файле как `PRAGMA user_version`.

## Язык артефактов

Язык выбирается по читателю артефакта, а не по файлу.

| № | Артефакт                                                            | Язык       |
|---|---------------------------------------------------------------------|------------|
| 1 | Код пакета `tg_export/`: комментарии, docstrings, имена              | английский |
| 2 | Вывод команд и тексты ошибок                                         | английский |
| 3 | Манифест `pyproject.toml`, скрипты `scripts/`, workflow `.github/`   | английский |
| 4 | Тесты `tests/`: docstrings и сообщения проверок                      | русский    |
| 5 | Документация: README, `docs/`, CHANGELOG, ADR, этот файл             | русский    |
| 6 | Шаблоны issue и pull request                                         | русский    |
| 7 | Сообщения коммитов                                                   | русский    |

Смысл разделения: строки 1--3 читает всякий, кто берёт пакет с PyPI или открывает
репозиторий со стороны, поэтому там английский; строки 4--7 обращены к тому, кто ведёт
проект. Строки 1--3 закреплены тестом
`tests/test_code_style.py::test_the_package_and_its_build_files_speak_english`: кириллица в
коде пакета, манифесте, скриптах или workflow роняет проверки.

## Формат коммитов

Используется [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```
<тип>(<область>): краткое описание

Опциональное расширенное описание.
```

Типы: `feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `perf`, `ci`.

Примеры из истории:

- `feat(tg): показывать msg_id в выводе messages, дедупликация файлов в download`
- `fix(terminal): эскейп rich-markup в именах чатов/файлов и устранение гонки в Live`
- `chore: подготовка к релизу v1.1.0`

## Pull request

- Один PR -- одна логическая задача. Если нужно несколько правок, разбейте на отдельные PR.
- Все тесты должны проходить перед merge.
- В описании PR кратко: что изменено и зачем, какие тесты добавлены. Шаблон с перечнем проверок
  подставляется автоматически (`.github/PULL_REQUEST_TEMPLATE.md`).
- Не добавляйте в репозиторий реальные данные Telegram (имена контактов, чатов, ID, экспортированные файлы).
- Артефакты сборки (`build/`, `dist/`, `*.egg-info`, `.coverage`) в git не попадают, но остаются в рабочем
  дереве и сбивают поиск по репозиторию: `build/lib/tg_export/` — копия пакета на момент сборки, и `rg` по
  имени функции находит её дважды. Убирать их командой `rm -rf build/ dist/ *.egg-info`.

Правила общения в issues и PR — [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).

## Безопасность данных

В коде, тестах, фикстурах, коммитах и любых файлах проекта запрещено использовать:

- реальные имена пользователей, контактов, чатов, групп, каналов;
- реальные Telegram ID;
- реальные api_id/api_hash, session-файлы;
- результаты экспорта `export_output/` (этот каталог и любые другие, содержащие реальные данные).

Используйте только вымышленные данные в примерах и тестах.

Найденную уязвимость не заводите публичным issue: порядок приватного сообщения
описан в [SECURITY.md](SECURITY.md).
