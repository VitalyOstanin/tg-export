# 0009 — Версионированная схема каталога медиа

- Статус: принято
- Дата: 2026-11-26

## Контекст

В upstream схема v1 сверяет недостающие столбцы при открытии. Таблица `files`
хранит одну запись на `(file_id, chat_id)` и не различает оригинал, миниатюру и
несколько источников. `export_state.full_history` относится только к legacy
обходу. Выводить из этих строк проверенные варианты или полноту Takeout нельзя.
Для Raw и независимой очереди нужны новые ключи и внешние связи. Установка
нескольких таблиц по одной оставила бы промежуточную схему при падении процесса.

## Рассмотренные варианты

1. Расширить `files` полями variant и использовать прежний ключ. Это не
   поддерживает несколько вариантов и источников без неоднозначной миграции.
2. Сразу перенести каждую старую строку `files` в `media_variants.original`.
   Старые записи не доказывают тип объекта и полноту файла.
3. Оставить legacy таблицы и добавить отдельный граф сущностей одной
   версионированной миграцией. Этот вариант принят.

## Решение

- Схема v2 в `tg_export/state.py` создаёт `media_assets`, `media_sources`,
  `media_variants`, `media_requests`, `media_jobs` и пустую `message_raw`.
  `PRAGMA user_version=2` записывается в той же транзакции, что и DDL.
- Перед изменением существующей БД создаётся приватный SQLite backup
  `*.pre-v2.bak` (следующие попытки получают числовой суффикс). Новый пустой
  файл в backup не нуждается. Ошибка создания backup останавливает миграцию.
- Старые `messages`, `files`, `export_state` остаются нетронутыми по смыслу;
  никакие legacy `files` автоматически не превращаются в `original`.
  Существующее согласование столбцов v1 выполняется до транзакции v2 и
  сохраняет старые правила совместимости. При сбое v2 версию 1 можно
  безопасно открыть повторно; новый граф либо есть целиком, либо отсутствует.
  База, у которой `messages` не имеет ключа `(chat_id,msg_id)`, отвергается до
  DDL v2: такой FK нельзя сделать надёжным простым добавлением столбцов.
- `media_assets` уникален по `(account_id, asset_kind, telegram_id)`.
  Составной FK источника `(asset_id, account_id)` запрещает чужой аккаунт.
  Составной FK запроса `(variant_id, asset_id)` запрещает вариант другого
  asset. `media_sources(chat_id,msg_id)` ссылается на `messages`; удаление
  сообщения удаляет только этот источник. Удаление asset, variant или job
  с зависимостями ограничено `RESTRICT`: очистка физических файлов явная.
- Одна физическая версия определяется `(asset_id, variant_key)`; несколько
  `media_requests` могут указывать на неё, а `media_jobs` имеет не более
  одной строки на `variant_id`. `no_thumbnail` хранится как результат запроса
  с `variant_id=NULL`, без фиктивного варианта или задания.
- `PRAGMA foreign_keys=ON` включается до записей на соединении `ExportState`.
  Статусы и базовые переходные формы ограничены `CHECK`. Канонизация
  `source_locator`, правила авторизации original, lease/retry и соответствие
  локального файла проверяются будущим DAO перед каждой записью/загрузкой.
  Повторное открытие v2 проверяет наличие всех шести таблиц и явно сообщает
  о неполной схеме. `message_raw` допускает ровно один payload для `saved` или
  только код ошибки для `raw_failed`.

## Последствия

Legacy загрузчик файлов и HTML пока используют прежние таблицы. При обычном
запуске экспорт истории теперь сохраняет нормализованное сообщение, Raw (либо
`raw_failed`), asset, source, выбранный вариант, request и задачу статической
миниатюры одним commit на пакет. Повторная запись того же сообщения не создаёт
дубликатов. Если безопасной миниатюры нет, пишется `no_thumbnail`, без задания
на оригинал. Очередь пока только пополняется: исполнитель, отдельная политика
медиа и загрузка варианта относятся к следующим шагам. Курсоры фаз остаются
на прежнем безопасном пути: повтор после сбоя может перечитать пакет, но не
пропускает его. Их объединение с пакетом требует изменения checkpoint модели
в T09. Чтение и repair legacy `files` пока также остаются на прежнем пути.

Проверки: `tests/test_media_schema.py` создаёт v1 БД с данными, открывает её
повторно, сверяет backup, имитирует сбой последнего DDL, проверяет откат и
повтор, составные FK, несколько запросов на один variant и commit/rollback
всего графа. `tests/test_history_capture.py` проверяет идемпотентную запись
Raw и очереди, откат пакета, явный `raw_failed` и отсутствие задания для
оригинала. Живой пользовательский архив в тестах не используется.

ADR-0003 остаётся описанием согласования столбцов legacy схемы; новая
версионированная миграция дополняет его для таблиц форка.
