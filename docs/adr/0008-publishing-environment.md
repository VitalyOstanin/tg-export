# 0008 — Публикация привязана к окружению GitHub

- Статус: принято
- Дата: 2026-08-23
- Заменяет: последнее последствие [0007](0007-split-publishing-permissions.md) — «GitHub Environment для публикующего job'а не заводится»

## Контекст

[0007](0007-split-publishing-permissions.md) свело право обменять OIDC-токен к одному job'у,
который ничего, кроме загрузки артефакта в PyPI, не делает. Тогда же было решено окружение
GitHub не заводить: настройка привязки к окружению живёт на стороне PyPI, а расхождение
обнаружилось бы отказом загрузки уже после сборки.

Решение опиралось на неполную картину. Пока имя окружения не названо ни в workflow, ни у
доверенного издателя, удостоверение OIDC выпускается **любому** прогону этого workflow — в том
числе запущенному с чужой ветки, если workflow туда попал. Окружение — единственное место, куда
вешается ручное подтверждение перед необратимым шагом: `yank` скрывает версию в PyPI, но не
освобождает номер.

Проверено по документации GitHub («Managing environments for deployment») и PyPI (Trusted
Publishers): GitHub создаёт окружение при первом упоминании в workflow автоматически и правил
защиты ему не даёт, поэтому строка в workflow сама по себе ничего не ломает и ручного
подтверждения не вводит. Поле окружения у доверенного издателя на PyPI необязательно, и пока оно
пустое, удостоверение принимается от любого прогона.

## Рассмотренные варианты

1. Оставить как в 0007 — окружение не заводить. Доверие остаётся широким, места для ручного
   подтверждения нет.
2. Объявить окружение в workflow и внести его имя у доверенного издателя на PyPI. Требует
   действия в веб-интерфейсе PyPI, которое конвейером не выполняется.
3. Объявить окружение только в workflow. Даёт место для ручного подтверждения, но доверия на
   стороне PyPI не сужает.

## Решение

Принят вариант 2. Публикующий job объявляет `environment: name: pypi` с URL проекта в PyPI, и то
же имя вносится в настройку доверенного издателя на стороне PyPI.

## Последствия

- Удостоверение OIDC принимается PyPI только от прогонов, прошедших через окружение `pypi`.
- Наличие окружения у публикующего job'а закреплено тестом
  `test_the_publishing_job_names_an_environment` (`tests/test_release.py`).
- Половина решения живёт вне репозитория: имя окружения нужно внести у доверенного издателя на
  PyPI вручную, и тестом это не проверяется. Пока поле там пустое, объявление в workflow сужения
  доверия не даёт — оно остаётся только местом для ручного подтверждения.
- Правила защиты (список тех, кто подтверждает релиз, задержка) окружению не заданы: GitHub
  создаёт его при первом использовании пустым. Ручное подтверждение добавляется отдельным
  действием в настройках репозитория.
