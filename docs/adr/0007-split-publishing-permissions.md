# 0007 — Разделение прав релизного конвейера по job'ам

- Статус: принято
- Дата: 2026-08-23

## Контекст

Публикация на PyPI идёт через Trusted Publishing: workflow запрашивает у GitHub OIDC-токен и
обменивает его на upload-token PyPI. Право на такой запрос даёт `permissions: id-token: write`.

Переменные `ACTIONS_ID_TOKEN_REQUEST_URL` и `ACTIONS_ID_TOKEN_REQUEST_TOKEN` GitHub кладёт в
окружение **каждого** шага job'а, объявившего это право, а не только того шага, который
публикует. Пока весь релиз выполнялся одним job'ом, право обменять токен имели и `uv sync`
(исполняет build-backend'ы и install-хуки пакетов из `uv.lock`), и `scripts/check.sh` (прогоняет
тесты проекта), и `uv build`, и smoke-проверка колеса.

Отсюда следовало: компрометация любой зависимости из `uv.lock` или правка тестов, попавшая в тег,
давала не сломанный релиз, а возможность выпустить в PyPI произвольный пакет от имени проекта.
Публикация необратима — `yank` скрывает версию, но не освобождает номер.

## Рассмотренные варианты

1. Оставить один job, положившись на то, что тег ставится с проверенной ветки. Право остаётся у
   всех шагов, то есть предмет замечания не устраняется.
2. Сузить набор шагов внутри job'а (например, ставить зависимости без dev-группы). Уменьшает
   поверхность, но токен по-прежнему доступен каждому оставшемуся шагу.
3. Разложить релиз на job'ы и выдать права по задачам, как описано в документации PyPA для
   Trusted Publishing.

## Решение

Принят вариант 3. `publish.yml` состоит из трёх job'ов:

- `build` — `contents: read`; установка зависимостей, `scripts/check.sh`, сверка тега с манифестом
  и CHANGELOG, сборка и smoke-проверка колеса; результат передаётся артефактами `dist` и
  `release-notes`;
- `publish` — `needs: build`, `id-token: write`; скачивание артефакта и `gh-action-pypi-publish`,
  никакого кода проекта;
- `github-release` — `needs: publish`, `contents: write`; создание GitHub Release из подготовленных
  release notes.

## Последствия

- Код, который проект не контролирует, выполняется без права обменять OIDC-токен.
- Порядок «всё, что может отказать, до необратимой публикации» сохранён и теперь выражен через
  `needs`, а не через порядок шагов внутри одного job'а (см. [0004](0004-release-gate-before-publishing.md)).
- Между job'ами добавлена передача через артефакты: `dist/` и `release_notes.md` больше не лежат в
  общем рабочем каталоге. Шаг, добавленный в `build` и производящий файл, нужный дальше, требует
  явной выгрузки.
- Требование к дальнейшим правкам закреплено тестом: в job'е с `gh-action-pypi-publish` не должно
  быть шагов `run`, а `id-token` не должен появляться у остальных job'ов.
- GitHub Environment для публикующего job'а не заводится: привязка Trusted Publisher к окружению
  настраивается на стороне PyPI, и расхождение настроек обнаружилось бы отказом загрузки уже после
  сборки. Ручное одобрение релиза, которое даёт окружение, при необходимости добавляется отдельно.
