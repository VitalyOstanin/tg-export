# 0001 — Использование ADR

- Статус: принято
- Дата: 2026-05-29

## Контекст

Проект имеет нетривиальную архитектуру (модули `api`, `auth`, `catalog`, `config`, `converter`,
`exporter`, HTML-рендеринг, sibling-дедупликация через hardlink, Takeout API). Значимые решения
ранее фиксировались только как поясняющие комментарии в коде (например, выбор `python-socks` в
`pyproject.toml`, обоснование `FixedSQLiteSession` в `tg_export/session.py`) и в большом
design-документе `docs/superpowers/specs/`. Единого места для пронумерованных архитектурных
решений не было, что затрудняет поиск обоснований и отслеживание их эволюции.

## Рассмотренные варианты

1. Не вести ADR, оставить обоснования в комментариях и design-документе.
2. Завести каталог ADR в формате MADR с пронумерованными записями.
3. Использовать формат Nygard (более лаконичный, без структурированных секций вариантов).

## Решение

Принят вариант 2: каталог `docs/adr/` в формате MADR. MADR даёт структурированные секции
(контекст, варианты, решение, последствия), что удобно для последующего чтения и сравнения.

## Последствия

- Новые значимые архитектурные решения фиксируются отдельной пронумерованной записью.
- Существующие обоснования в комментариях и design-документе остаются в силе; переносить их
  в ADR задним числом не требуется.
- При изменении ранее принятого решения добавляется новая запись со статусом, ссылающимся на
  предыдущую (`superseded by`), без переписывания старой.
