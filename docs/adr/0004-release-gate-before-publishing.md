# 0004 — Проверки до необратимой публикации

- Статус: принято
- Дата: 2026-08-22

## Контекст

Публикация на PyPI необратима: версию нельзя перезалить и нельзя снять так, чтобы номер
освободился. При этом релизный путь запускается тегом, а workflow проверок на `push` тега не
срабатывает — на релизном пути стоял только прогон `pytest`.

Отсюда следовали два наблюдаемых отказа: тег на коммите с рассинхронизированным `uv.lock` или с
ошибками типов публиковался беспрепятственно; отсутствующий раздел `CHANGELOG.md` обнаруживался
проверкой `test -s release_notes.md`, стоявшей ниже загрузки, — версия уходила в индекс,
GitHub Release не создавался, а workflow краснел уже после.

## Рассмотренные варианты

1. Полагаться на то, что тег ставится с ветки, проверенной обычным CI.
2. Прогонять проверки на релизном пути, но после сборки пакета — ближе к публикации.
3. Выстроить релизный путь так, чтобы всё, что может отказать, отрабатывало строго до загрузки
   на PyPI.

## Решение

Принят вариант 3. Порядок шагов `publish.yml` подчинён одному правилу: сначала всё, что может
сказать «нет», и только потом необратимый шаг.

1. `scripts/check.sh` — тот же набор, что и на CI: синхронизация `uv.lock`, линтер, формат, типы,
   тесты, границы покрытия по модулям.
2. `scripts/release_notes.py <тег>` — тег совпадает с версией в `pyproject.toml`, раздел в
   `CHANGELOG.md` существует и не пуст.
3. `uv build` и smoke-тест wheel — пакет собирается, шаблоны и статика на месте.
4. Публикация на PyPI.
5. Создание GitHub Release.

Тот же скрипт проверок доступен локально, а расхождение состава шагов между ним и CI ловится
тестом.

## Последствия

- Отказ любого рода обнаруживается до того, как версия занята.
- Релизный прогон дольше: набор проверок выполняется дважды — на ветке и на теге. Это принятая
  цена необратимости публикации.
- Сверка тега с манифестом и `CHANGELOG.md` доступна локально до создания тега
  (`scripts/release_notes.py vX.Y.Z --output ...`).
