## Шаги релиза

1. Обновить версию в `pyproject.toml`.
2. Выполнить `uv lock` и закоммитить обновлённый `uv.lock` в том же коммите.
3. Переименовать раздел `## [Не выпущено]` в `CHANGELOG.md` в `## [X.Y.Z] -- ГГГГ-ММ-ДД` (формат Keep a Changelog); номер версии и дата должны совпадать с тегом, а раздел не должен быть пустым.
4. Убрать артефакты прошлых сборок: `rm -rf build/ dist/ *.egg-info`. Каталог `build/` — распакованная
   копия пакета, оставшаяся от прямой сборки колеса; он не попадает ни в коммит, ни в дистрибутив
   (`uv build` собирает из sdist), но остаётся в рабочем дереве и виден поиску `rg` и индексации IDE:
   каждое имя функции находится дважды, и второе совпадение — устаревшее.
5. Прогнать проверки локально: `scripts/check.sh`.
6. Сверить согласованность будущего релиза, не создавая тега: `uv run python scripts/release_notes.py vX.Y.Z --output /tmp/release_notes.md`. Скрипт откажет, если тег расходится с версией манифеста или раздела в `CHANGELOG.md` нет.
7. Закоммитить, создать тег (см. ниже), запушить тег -- workflow `publish.yml` прогонит тот же набор проверок, сверит тег с манифестом и CHANGELOG, соберёт пакет, выполнит smoke-тест wheel и опубликует на PyPI.

## Гейт перед публикацией

Порядок шагов в `publish.yml` подчинён одному правилу: всё, что может отказать, отрабатывает до
загрузки на PyPI, потому что откатить публикацию нельзя.

| № | Шаг                                  | Что проверяет                                                              |
|---|--------------------------------------|----------------------------------------------------------------------------|
| 1 | `scripts/check.sh`                   | синхронизация `uv.lock`, линтер, формат, типы, тесты, границы покрытия      |
| 2 | `scripts/release_notes.py <тег>`      | тег = версия в `pyproject.toml`; раздел `CHANGELOG.md` существует и не пуст |
| 3 | `uv build` и smoke-тест wheel         | пакет собирается, шаблоны и статика на месте, индексная страница рендерится |
| 4 | публикация на PyPI                    | необратимый шаг -- выполняется последним из проверяемых                     |
| 5 | `gh release create`                   | GitHub Release из подготовленных на шаге 2 release notes                    |

Прежде из этого набора перед публикацией выполнялись только тесты, а единственная проверка
`CHANGELOG.md` стояла ниже загрузки на PyPI: отсутствующий раздел давал опубликованную версию,
отсутствующий GitHub Release и красный workflow.

## Теги

- Релизные теги именуются `vX.Y.Z` (валидный semver).
- Создавать **аннотированные** теги, а не lightweight: `git tag -a vX.Y.Z -m "vX.Y.Z"`. Аннотированный тег хранит автора, дату и сообщение и поддерживает подпись.
- Подписывать тег, если настроен ключ: `git tag -s vX.Y.Z -m "vX.Y.Z"` (GPG) либо
  `git -c gpg.format=ssh -c user.signingkey=<путь к ключу> tag -s vX.Y.Z -m "vX.Y.Z"` (SSH).
  Подпись тега удостоверяет, кто выпустил версию; аттестации PEP 740 удостоверяют, каким workflow
  собран артефакт. Это разные утверждения, и одно не заменяет другое. Ключа нет — тег остаётся
  аннотированным без подписи, релиз это не блокирует.
- Уже опубликованные lightweight-теги (`v1.0.0`, `v1.1.0`, `v1.2.7`) не переписывать -- на них завязан запуск `publish.yml`. Конвенция действует для будущих тегов.

## Публикация

- Публикация на PyPI выполняется через Trusted Publishing (OIDC, `id-token: write` в `publish.yml`) -- долгоживущий токен PyPI не используется.
- Перед публикацией `publish.yml` прогоняет весь набор проверок (`scripts/check.sh`), сверку тега с манифестом и CHANGELOG, а также smoke-тест собранного wheel.
- Артефакты публикуются с аттестациями PEP 740: параметр `attestations: true` задан в `publish.yml` явно.
  Значение совпадает с умолчанием действия, но умолчание может измениться, а публикация необратима —
  потерю аттестаций заметили бы не сразу. Аттестации работают только вместе с Trusted Publishing.
