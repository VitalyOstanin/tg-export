## Шаги релиза

1. Обновить версию в `pyproject.toml`.
2. Выполнить `uv lock` и закоммитить обновлённый `uv.lock` в том же коммите.
3. Переименовать раздел `## [Не выпущено]` в `CHANGELOG.md` в `## [X.Y.Z] -- ГГГГ-ММ-ДД` (формат Keep a Changelog) и добавить строку о новой версии в раздел «Содержание» того же файла: оглавление ведётся вручную, а его соответствие разделам проверяется тестом. Номер версии и дата должны совпадать с тегом, а раздел не должен быть пустым. Номер выбирается по содержимому раздела: «Ломающие изменения» требуют бампа major, «Добавлено» -- не ниже minor, остальное выпускается как patch.
4. Убрать артефакты прошлых сборок: `rm -rf build/ dist/ *.egg-info`. Каталог `build/` — распакованная
   копия пакета, оставшаяся от прямой сборки колеса; он не попадает ни в коммит, ни в дистрибутив
   (`uv build` собирает из sdist), но остаётся в рабочем дереве и виден поиску `rg` и индексации IDE:
   каждое имя функции находится дважды, и второе совпадение — устаревшее.
5. Прогнать проверки локально: `scripts/check.sh`.
6. Сверить согласованность будущего релиза, не создавая тега: `uv run python scripts/release_notes.py vX.Y.Z`. Без `--output` notes печатаются в stdout и файла в рабочем дереве не остаётся. Скрипт откажет, если тег расходится с версией манифеста, раздела в `CHANGELOG.md` нет, выбранный номер меньше, чем требует содержимое раздела, или дата раздела расходится с датой тега больше чем на сутки (последнее проверяется, когда передан `--tag-date`; в `publish.yml` он передаётся всегда).
7. Закоммитить правки и запушить `master` -- без тега. Репетиция ниже идёт по коду, который уже в `origin`.
8. Отрепетировать конвейер до постановки тега: `gh workflow run publish.yml --ref master` (либо кнопка Run workflow на вкладке Actions). Репетиция проходит job сборки целиком -- сверку номера с манифестом и CHANGELOG, весь набор проверок, сборку пакета, smoke-тест wheel и выгрузку артефактов, -- а job публикации и job создания release пропускает. Это единственный способ проверить механизмы, отказ которых виден только в прогоне: передачу `dist/` и `release_notes.md` между job'ами и поведение самих шагов на runner'е. Номер берётся из манифеста ветки, дата раздела при репетиции не сверяется.
9. Создать тег (см. ниже) и запушить его -- workflow `publish.yml` прогонит тот же набор проверок, сверит тег с манифестом и CHANGELOG, соберёт пакет, выполнит smoke-тест wheel и опубликует на PyPI.

## Гейт перед публикацией

Порядок шагов в `publish.yml` подчинён одному правилу: всё, что может отказать, отрабатывает до
загрузки на PyPI, потому что откатить публикацию нельзя.

| № | Шаг                                  | Что проверяет                                                              |
|---|--------------------------------------|----------------------------------------------------------------------------|
| 1 | `scripts/check.sh`                   | синхронизация `uv.lock`, линтер, формат, типы, тесты, границы покрытия      |
| 2 | `scripts/release_notes.py <тег>`      | тег = версия в `pyproject.toml`; раздел `CHANGELOG.md` существует, не пуст, не требует бампа крупнее выбранного и датирован днём тега (допуск -- сутки) |
| 3 | `uv build` и smoke-тест wheel         | пакет собирается, шаблоны и статика на месте, индексная страница рендерится |
| 4 | публикация на PyPI                    | необратимый шаг -- выполняется последним из проверяемых                     |
| 5 | `gh release create`                   | GitHub Release из подготовленных на шаге 2 release notes                    |

Прежде из этого набора перед публикацией выполнялись только тесты, а единственная проверка
`CHANGELOG.md` стояла ниже загрузки на PyPI: отсутствующий раздел давал опубликованную версию,
отсутствующий GitHub Release и красный workflow.

Набор разложен на три job'а, и права выданы по задачам, а не всему конвейеру. `build` (шаги 1--3)
идёт с `contents: read` и отдаёт `dist/` и `release_notes.md` артефактами. `publish` (шаг 4)
получает `id-token: write` и состоит только из скачивания артефакта и загрузки на PyPI.
`github-release` (шаг 5) идёт с `contents: write`. Причина: GitHub кладёт переменные запроса
OIDC-токена в окружение каждого шага job'а, объявившего `id-token`, поэтому в едином job'е
получить upload-token PyPI мог любой шаг -- включая `uv sync`, исполняющий build-backend'ы
зависимостей, и прогон тестов.

## Теги

- Релизные теги именуются `vX.Y.Z` (валидный semver).
- Pre-release-номера (`vX.Y.Zrc1`, `vX.Y.Z-beta` и подобные) конвейером не выпускаются. Гейт
  отказывает на любом номере не вида `X.Y.Z`: размер бампа сверяется с номером раздела ниже в
  `CHANGELOG.md`, а pre-release не является ни шагом вверх, ни шагом вниз -- такой номер
  проходил проверку размера нетронутым и попадал на GitHub помеченным `--latest`, то есть
  выдавался за очередной выпуск. Понадобится pre-release -- вводить его вместе с разбором
  номера в гейте и пометкой `--prerelease` в шаге создания release.
- Создавать **аннотированные** теги, а не lightweight: `git tag -a vX.Y.Z -m "vX.Y.Z"`. Аннотированный тег хранит автора, дату и сообщение и поддерживает подпись.
- Подписывать тег, если настроен ключ: `git tag -s vX.Y.Z -m "vX.Y.Z"` (GPG) либо
  `git -c gpg.format=ssh -c user.signingkey=<путь к ключу> tag -s vX.Y.Z -m "vX.Y.Z"` (SSH).
  Подпись тега удостоверяет, кто выпустил версию; аттестации PEP 740 удостоверяют, каким workflow
  собран артефакт. Это разные утверждения, и одно не заменяет другое. Ключа нет — тег остаётся
  аннотированным без подписи, релиз это не блокирует.
- Тег ставится только на коммит, достижимый из `master`. Workflow срабатывает на любой тег `v*`, а
  проверки о ветках ничего не знают, поэтому тег на рабочей ветке или на коммите до вливания
  опубликовал бы версию, содержимое которой в `master` не попадало. Достижимость сверяется гейтом
  (`git merge-base --is-ancestor`) до сборки.
- Уже опубликованные lightweight-теги (`v1.0.0`, `v1.1.0`, `v1.2.7`) не переписывать -- на них завязан запуск `publish.yml`. Конвенция действует для будущих тегов.

## Публикация

- Публикация на PyPI выполняется через Trusted Publishing (OIDC, `id-token: write` в `publish.yml`) -- долгоживущий токен PyPI не используется.
- Перед публикацией `publish.yml` прогоняет весь набор проверок (`scripts/check.sh`), сверку тега с манифестом и CHANGELOG, а также smoke-тест собранного wheel.
- Job публикации привязан к окружению `pypi`. Само по себе окружение ничего не запрещает, но его имя
  указывается у доверенного издателя на стороне PyPI: тогда удостоверение OIDC принимается только от
  прогона в этом окружении, а не от любого прогона workflow. Там же -- место для ручного
  подтверждения и списка тех, кто его даёт, если оно понадобится перед необратимым шагом. Окружение
  создаётся GitHub при первом использовании и правил защиты не получает.
- Артефакты публикуются с аттестациями PEP 740: параметр `attestations: true` задан в `publish.yml` явно.
  Значение совпадает с умолчанием действия, но умолчание может измениться, а публикация необратима —
  потерю аттестаций заметили бы не сразу. Аттестации работают только вместе с Trusted Publishing.

## Восстановление после отказа

Отказ до загрузки на PyPI обратим: тег удаляется (`git tag -d vX.Y.Z` и `git push --delete origin
vX.Y.Z`), причина устраняется, тег ставится заново. Ничего опубликованного за таким отказом не
остаётся -- в этом и состоит смысл порядка шагов.

Отказ после загрузки на PyPI необратим: версия уже в индексе, и номер считается израсходованным.
Порядок действий:

| № | Случай                                          | Что делать                                                                                     |
|---|-------------------------------------------------|------------------------------------------------------------------------------------------------|
| 1 | загрузка прошла, GitHub Release не создан        | перезапустить workflow: загрузка версии, уже лежащей в индексе, пропускается (`skip-existing`), а создание release идемпотентно |
| 2 | перезапуск не помогает (сбой API, лимит запросов) | создать release вручную: `gh release create vX.Y.Z --notes-file release_notes.md --latest`       |
| 3 | в индексе оказалась неполная или негодная версия | выпустить следующий patch; прежний номер не переиспользуется -- PyPI не принимает повторную загрузку файла |
